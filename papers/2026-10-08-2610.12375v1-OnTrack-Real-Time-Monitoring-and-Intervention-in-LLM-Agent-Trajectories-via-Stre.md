# OnTrack: Real-Time Monitoring and Intervention in LLM Agent Trajectories via Streaming Structure-Aware Optimal Transport

**Authors:** Babak Barazandeh, Connor Swanson, Chinmay Kulkarni, Nikhil Mungel
**Published:** 2026-10-08 | **arXiv:** [2610.12375v1](http://arxiv.org/abs/2610.12375v1)

## Summary
This paper introduces OnTrack, a real-time monitoring system that watches LLM agents as they execute tasks and detects when they're going off-track — then can halt them before they waste compute or cause damage. The key insight is using optimal transport to compare an agent's current trajectory against successful reference runs, all while maintaining millisecond-scale latency. This matters because autonomous LLM agents deployed in high-stakes domains (trading, IT incident response) can take irreversible actions; catching failures early saves cost and prevents harm.

## Theoretical Background
The paper builds on two core concepts: (1) agent trajectory monitoring — the problem of supervising autonomous systems in real time, and (2) optimal transport — a mathematical framework for comparing probability distributions or sequences of states by finding the minimal "cost" to transform one into another. Optimal transport has roots in computational geometry and has recently been applied to comparing high-dimensional sequences in machine learning. The work also relates to safeguarding mechanisms in LLM systems, which traditionally either run a second "monitor agent" (expensive, adds latency per step) or evaluate logs post-hoc (too late to intervene).

## Core Contributions
1. **OnTrack architecture**: A streaming, structure-aware monitoring system that operates at ~1 millisecond per agent step, comparing step dependencies and sequences against reference trajectories without requiring full plan predictions.
2. **Graceful degradation**: The method works across three realistic access regimes — with full reference runs + schemas, with only tool schemas, or with only step logs — and degrades gracefully in capability (from plan violation detection to loop/stall detection).
3. **Empirical validation on SWE-bench**: Demonstrated that after just 8 steps, OnTrack ranks failing trajectories below passing ones better than content-similarity baselines (+0.057 AUROC), and an abort policy saves ~18% of wasted compute on doomed runs.
4. **Optimal transport formulation**: Novel application of streaming optimal transport to agent monitoring, enabling efficient comparison of trajectory structure without dense semantic embedding.

## Connections to Other Work
OnTrack addresses the middle ground between [[RLHF]] and constitutional AI (post-hoc value alignment) and runtime safeguarding systems. It relates to [[mechanistic-interpretability]] work in that it reasons about agent decision sequences structurally rather than semantically. The paper contrasts itself with: (a) safeguard agents (e.g., monitoring via a second LLM), which incur latency; (b) post-hoc evaluation (e.g., log analysis after failure), which cannot intervene; and (c) planning-based approaches that predict full trajectories. It also touches on agent evaluation and anomaly detection in sequential systems — areas active in both NLP and reinforcement learning communities.

## Practical Applications
1. **Autonomous trip planners**: Halt agents booking flights or hotels if they deviate from user preferences before committing charges.
2. **Stock trading bots**: Detect and stop an agent executing a trade sequence that violates risk constraints or repeats failed strategies.
3. **IT incident triage**: Prevent automated incident response systems from performing destructive actions (e.g., terminating production services) when early steps signal hallucination or loop behavior.
4. **Cloud resource provisioning**: Monitor infrastructure-as-code agents and abort if they deviate from approved deployment templates.
5. **Customer support automation**: Catch escalation loops or repetitive queries and redirect to human agents before burning chat tokens.

## Product & Startup Ideas
1. **LLM Agent Watchdog (SaaS)**: A monitoring API that integrates with existing agent frameworks (LangChain, AutoGPT) — upload reference trajectories, set thresholds, and get real-time alerts + abort triggers for agents going off-track. Charge per monitored agent or per-million-steps.
2. **Enterprise Agent Governance Platform**: Bundle OnTrack with audit logging, compliance policy templates, and cost analytics for enterprises running autonomous agents across critical workflows (finance, operations). Positioning: "Agent guardrails as a service."
3. **Agent Trajectory Debugger IDE**: A developer tool for building and testing agents that visualizes successful vs. failing trajectories in real time and suggests which agent behaviors are anomalous before deployment.
4. **Anomaly Detection for Autonomous Systems**: Extend OnTrack to robotics/embodied agents; sell a hardware-agnostic monitoring layer that compares physical task trajectories (via sensor logs) to learned success patterns.
5. **Agent Insurance / Cost Optimization Layer**: Offer a subscription service that insures LLM agent runs against runaway costs — OnTrack detects failures early, reducing claims, positioning as "failure prediction for autonomous systems."

## Technical Limitations
1. **Dependence on reference data**: In the "full access" regime, performance degrades sharply without high-quality, diverse historical runs. Biased or limited training trajectories will cause false negatives (missing real failures).
2. **Optimal transport compute**: While claimed to be ~1ms per step, optimal transport scales poorly with trajectory length and state dimensionality. May become impractical for very long-horizon tasks or high-dimensional tool outputs.
3. **Structure vs. semantics**: OnTrack reasons about step sequence structure (loops, stalls) but may miss semantic failures — e.g., an agent takes syntactically correct but semantically nonsensical steps that don't form a loop.
4. **Tool schema assumptions**: In intermediate access regime, assumes tool schemas are accurate and stable; if schemas change or are incomplete, the method loses signal.
5. **No learning**: OnTrack is static; it does not adapt to the specific agent's behavior over time or learn from correction feedback. Each deployment requires offline configuration.
6. **Evaluation scale**: Validation is limited to SWE-bench (software engineering tasks). Generalization to other domains (trading, customer service) is untested.

## Open Questions
1. How does OnTrack perform on longer-horizon tasks (>100 steps)? Does optimal transport scaling become prohibitive?
2. Can the method be extended to **online learning** — i.e., update reference trajectories and thresholds in response to user feedback or new failures?
3. What is the false positive rate in production? The paper reports 5/6 aborts were correct; what happens with a larger corpus?
4. How does OnTrack handle **distribution shift** — e.g., when the deployment environment differs from reference runs used to train monitoring thresholds?
5. Can this be combined with [[mechanistic-interpretability]] to explain *why* an agent is off-track, not just detect it?
6. Does OnTrack work for **multi-agent systems** where agents coordinate or compete? How should dependencies be tracked across agents?

## Key Takeaway
Real-time agent monitoring using optimal transport catches failing trajectories within milliseconds, stopping costly errors before they compound.
