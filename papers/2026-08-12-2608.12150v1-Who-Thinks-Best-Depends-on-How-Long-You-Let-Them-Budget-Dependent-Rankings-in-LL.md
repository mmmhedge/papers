# Who Thinks Best Depends on How Long You Let Them: Budget-Dependent Rankings in LLM Evaluation

**Authors:** Rodrigo Guedes de Souza, Alison R. Panisson
**Published:** 2026-08-12 | **arXiv:** [2608.12150v1](http://arxiv.org/abs/2608.12150v1)

## Summary
This paper challenges the standard assumption that large language model rankings stay the same across different inference conditions. By testing four models on reasoning benchmarks with varying token budgets (64–4,096 tokens), the authors show that model performance and relative rankings shift dramatically depending on how much computational budget each model gets, sometimes reversing completely. This matters because current evaluation practices treat models as having fixed, stable rankings—but in reality, "best" depends heavily on the constraints.

## Theoretical Background
LLM evaluation traditionally uses fixed inference conditions (e.g., all models generate up to some token limit) and assumes these conditions produce stable, comparable rankings. This approach inherits from machine learning evaluation, where benchmarks aim to measure intrinsic model capacity independent of deployment details. The paper tests this on reasoning benchmarks—tasks requiring multi-step problem solving where token budget plausibly affects strategy and output quality. The oracle analysis concept (measuring what a hypothetical perfect selector could achieve using all models' outputs) comes from ensemble learning and model mixture literature.

## Core Contributions
1. **Empirical demonstration of budget-dependent rankings**: Across three reasoning benchmarks, model rankings reverse significantly ($p < 0.01$) depending on token budget, contradicting the stable-ranking assumption.
2. **Non-monotone accuracy behavior**: 3–19% of test items show accuracy *decreasing* as budget increases, a puzzling phenomenon that persists even after controlling for truncation, and varies model-to-model (only 6–14% cross-model overlap).
3. **Oracle complementarity analysis**: When selectively using the best-performing model per item at each budget level, performance improves up to +27.8 percentage points, with strongest gains at constrained budgets.
4. **Budget-aware routing**: A router model that selects which model to use based on budget achieves 14.1% of the oracle gap cross-domain, though budget features don't transfer well between datasets.

## Practical Applications
1. **Inference budgeting for production systems**: When deploying LLMs under latency or cost constraints, this shows you cannot assume a single "best" model—you must re-evaluate or use routing under your actual budget.
2. **Token allocation optimization**: For applications with variable budgets (e.g., user queries with different complexity), this suggests adaptive allocation—some queries may need fewer tokens than others to reach good performance.
3. **Cost-performance tradeoffs in APIs**: LLM API providers (OpenAI, Anthropic, etc.) could use budget-aware routing to serve different SLAs (speed vs. accuracy) more efficiently.
4. **Cascading inference pipelines**: Route simple queries to constrained models, reserve high-budget models for hard problems—requires knowing budget-performance profiles per model.

## Product & Startup Ideas
1. **Budget-Aware Model Selector (B2B SaaS)**: A middleware service that profiles your LLMs at multiple token budgets on your specific task, then routes queries to the best model per budget in real-time. Reduces inference costs and latency.
2. **LLM Evaluation Platform**: Automated benchmarking tool that tests models across budget levels and generates budget-conditioned scorecards, replacing single-number rankings.
3. **Adaptive LLM Router**: Deployed as a lightweight model that predicts required token budget per query (simple queries → low budget, complex → high), then selects the best model for that budget, minimizing cost while maintaining quality.
4. **Inference Cost Optimizer**: For enterprises running multiple LLMs, automatically profiles and builds budget-performance curves, then schedules inference to minimize total cost across their workload.
5. **LLM Leaderboard (Consumer)**: Public leaderboard showing not one ranking but budget-stratified rankings, helping users pick the right model for their latency/cost constraints.

## Technical Limitations
1. **Limited model and benchmark coverage**: Only four models and three reasoning benchmarks tested. Findings may not generalize to other model families (e.g., smaller instruction-tuned models, multimodal models) or task types (generation, translation, retrieval).
2. **Unclear causality of non-monotone behavior**: The paper documents that accuracy sometimes *decreases* with more tokens but doesn't fully explain why (decoding diversity? pathological long-form outputs? benchmark artifacts?). This is a black box.
3. **Router generalization failure**: The budget-aware router transfers poorly across domains (−1.2pp), suggesting the learned patterns are task-specific. Real-world deployment would require per-domain retraining.
4. **Truncation effects not fully isolated**: While the authors control for truncation, the interplay between token budget and actual model stopping behavior (e.g., end-of-sequence tokens) remains partially confounded.
5. **No cost-benefit analysis**: The paper doesn't weigh the oracle gains against routing overhead or computational cost of maintaining multiple models.

## Open Questions
1. **Why does accuracy decrease with more tokens on some items?** A mechanistic investigation (probing model hidden states, analyzing generated text) could reveal whether this is inherent to the model, a decoding artifact, or a benchmark issue.
2. **Can we predict which items will exhibit non-monotone behavior?** If certain question types or models are prone to this, could we build a pre-screening step?
3. **Do findings hold for smaller models or non-reasoning tasks?** Code generation, summarization, translation likely have different budget-sensitivity profiles.
4. **What is the optimal allocation strategy?** Given a fixed total token budget across multiple queries, how should you distribute it across models and queries to maximize aggregate performance?
5. **Can we design better routers that transfer cross-domain?** What features (query difficulty, model capability, task type) would enable generalizable routing?

## Key Takeaway
Model rankings shift across token budgets, so "best model" depends on inference cost constraints—one-size-fits-all evaluation misses real-world performance.
