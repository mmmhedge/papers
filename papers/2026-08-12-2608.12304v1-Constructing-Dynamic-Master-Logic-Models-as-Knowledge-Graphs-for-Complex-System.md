# Constructing Dynamic Master Logic Models as Knowledge Graphs for Complex System Diagnostics Using Retrieval-Augmented Large Language Models

**Authors:** Saman Marandi, Yu-Shu Hu, Mohammad Modarres
**Published:** 2026-08-12 | **arXiv:** [2608.12304v1](http://arxiv.org/abs/2608.12304v1)

## Summary
This paper automates the construction of Dynamic Master Logic (DML) models — hierarchical diagrams that map system functions to physical components — by using large language models (LLMs) with retrieval-augmented generation to extract information from technical documentation and represent it as knowledge graphs. The approach makes it practical to build detailed diagnostic models for complex systems like nuclear reactors without relying entirely on human experts, and demonstrates that the automated models can reliably support reasoning about system failures and dependencies.

## Theoretical Background
Dynamic Master Logic is a well-established framework in reliability and safety engineering for representing complex systems hierarchically: it connects high-level functional objectives (what the system must do) down through intermediate logical gates and failure modes to physical components (what it has). Knowledge graphs are structured representations of entities and their relationships, often used to organize and reason about domain knowledge. Retrieval-augmented generation (RAG) is a technique that combines LLMs with document retrieval — the system finds relevant passages from a knowledge base before generating answers, reducing hallucination and grounding responses in actual source material. This paper uses RAG to extract function-to-component mappings from technical documentation, then structures those mappings as knowledge graphs that preserve both the logical gates (AND, OR) and the hierarchical dependencies of the original DML framework.

## Core Contributions
1. A scalable automated framework for constructing DML models from unstructured technical documentation using LLMs + RAG, extending prior work from toy systems to substantially larger, real-world systems.
2. Representation of DML as executable knowledge graphs (KG-DML) that support multiple types of reasoning: diagnostic (what caused a failure?), dependency tracing (what depends on this component?), upward propagation (how does a component failure affect system function?), and safety assessment.
3. A multi-level validation methodology that evaluates layer-by-layer precision and recall, verifies logical gate consistency, and assesses overall structural integrity — not just whether the graph "looks right," but whether it accurately preserves functional logic.
4. Demonstrated applicability to a real nuclear reactor subsystem (Low-Pressure Coolant Injection) with consistent reproducibility across repeated construction runs.

## Connections to Other Work
This work sits at the intersection of knowledge engineering, LLM applications, and safety-critical system modeling. It relates to [[RAG]] approaches for grounding LLM outputs in domain documents, similar to work on question-answering over technical manuals. The knowledge graph representation connects to work on ontology learning and automated extraction of system models from text. In the safety and reliability domain, this complements existing approaches to failure mode and effects analysis (FMEA) and fault tree analysis (FTA), but automates the tedious documentation-to-model translation step. The validation methodology echoes structured evaluation approaches in knowledge graph construction.

## Practical Applications
- **Nuclear facility decommissioning and maintenance**: Rapidly rebuild diagnostic and dependency models when facility documentation is incomplete or legacy systems lack modern documentation.
- **Industrial safety audits**: Automatically extract system architectures from equipment manuals and technical records to identify hidden failure propagation paths that manual inspection might miss.
- **Complex infrastructure diagnostics**: Apply to chemical plants, power grids, aircraft systems, or manufacturing lines where failure propagation must be traced quickly during incidents.
- **Knowledge preservation**: When expert operators or engineers retire, automatically capture the logical relationships between system functions and components embedded in existing technical documents, reducing knowledge loss.
- **Compliance and traceability**: Generate auditable, machine-readable models of system dependencies for regulatory documentation (e.g., nuclear safety case reports, aviation certification).

## Product & Startup Ideas
1. **SafeDoc AI**: A SaaS platform that ingests technical documentation (PDFs, manuals, CAD files) and automatically generates interactive failure propagation diagrams and diagnostic decision trees for plant operators and safety engineers; sells to utilities, refineries, and manufacturing.
2. **FailureChain Analytics**: Enterprise software that constructs and maintains knowledge graphs of system dependencies from live documentation repositories, then detects risk hotspots (high-criticality components with complex downstream effects) and alerts teams to vulnerabilities.
3. **LegacyLogic**: Specialized consulting tool for decommissioning and asset retirement; automatically reconstructs system models from decades-old plant records to enable safe dismantling and regulatory sign-off, particularly for nuclear and chemical facilities.
4. **DiagnoBot for Field Service**: Mobile app / edge AI deployed to technician tablets that lets them photograph equipment, extract component relationships from embedded manuals using RAG, and interactively trace failures in real time during on-site diagnosis.
5. **Regulatory AutoCompliance**: Software that transforms an operator's system description into formal knowledge graphs that automatically generate sections of safety case reports, failure analysis documentation, and dependency traceability matrices required by regulators.

## Technical Limitations
- **Hallucination and extraction errors**: While RAG reduces hallucination, LLMs may still misinterpret ambiguous technical prose, misidentify functional boundaries, or invent logical relationships not actually stated in documentation. The paper does not explore robustness to deliberately vague or contradictory source material.
- **Incomplete or legacy documentation**: Real systems often have inconsistent, outdated, or partially missing documentation. The method's performance degrades if key function-component links are not explicitly stated anywhere in available documents.
- **Scalability of validation**: The multi-level validation requires human review to verify logical gates and structural integrity. For very large systems (thousands of components), manual spot-checking becomes impractical.
- **No temporal dynamics**: DML is static; the framework does not model how system behavior, dependencies, or failure modes change over time, across operating modes, or under environmental stress — all common in real-world complex systems.
- **Limited to technical documentation**: The approach assumes quality technical documentation exists; it cannot infer missing relationships from first-principles physics or hidden interdependencies that operators know but never wrote down.
- **Knowledge graph complexity**: As systems grow, the knowledge graph can become unwieldy and computationally expensive to query; no discussion of compression, abstraction, or hierarchical querying strategies.

## Open Questions
- How sensitive is the framework to LLM choice, prompt design, and RAG retrieval quality? Does performance degrade gracefully with weaker models, or does it collapse?
- Can the method learn or refine logical gates iteratively as operators provide feedback on diagnoses (e.g., "the system did not fail in this way despite the model predicting it would")? How would that feedback loop work?
- How does the framework handle systems with modal behavior — different functional architectures under different operating states (e.g., normal, startup, emergency shutdown)? Can DML-KG represent multiple modes?
- Can automated confidence scores or uncertainty quantification be assigned to extracted relationships, so operators know which diagnostic inferences are well-grounded vs. speculative?
- Does the approach scale to cross-system dependencies (e.g., how does the LPCI system interact with the reactor control system)? How are system boundaries managed?
- Can the framework detect contradictions or inconsistencies across different technical documents, and flag them for human resolution?

## Key Takeaway
LLMs with knowledge graphs can automate the translation of complex system documentation into diagnostic models, reducing expert effort and enabling fast failure analysis in safety-critical settings.
