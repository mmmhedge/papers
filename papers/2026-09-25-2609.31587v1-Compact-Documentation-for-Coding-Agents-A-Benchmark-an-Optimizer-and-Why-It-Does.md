# Compact Documentation for Coding Agents: A Benchmark, an Optimizer, and Why It Does Not Transfer

**Authors:** Md Shohel Arman, Igor Molybog
**Published:** 2026-09-25 | **arXiv:** [2609.31587v1](http://arxiv.org/abs/2609.31587v1)

## Summary
This paper investigates whether natural-language documentation helps AI agents fix software bugs, and reports a surprising negative finding: better documentation doesn't actually improve agent performance when source code is available. The authors build a benchmark to measure documentation quality and an optimizer to improve it, showing that documentation completeness matters — but ultimately, the agents solve issues equally well using just the issue description alone.

## Theoretical Background
The work builds on two foundational ideas: (1) that code-understanding tasks benefit from auxiliary information (similar to how humans use documentation when reading unfamiliar code), and (2) that language models — neural networks trained to predict text sequences — can be guided by high-quality prompts and context to perform better on downstream tasks. Recent work on code generation has shown that models like GPT-4 or specialized coding models can resolve GitHub issues when given appropriate context. The paper also leverages the concept of a "roundtrip" evaluation: if you describe code in natural language, can another system regenerate code that passes the same tests? This is a proxy for documentation fidelity.

## Core Contributions
1. **Roundtrip benchmark**: A method to automatically score documentation quality by regenerating code from descriptions and checking test passage. Shows that *completeness* (not brevity) drives fidelity.
2. **Description optimizer**: A prompt-engineering approach that discovers high-fidelity descriptions generalizing to unseen files — reaching 100% test-passing regeneration.
3. **Negative result on transfer**: Demonstrates empirically across two model families and ten repositories that better documentation does not improve agent performance on real GitHub issues when source code is available.
4. **Boundary characterization**: Identifies specific conditions under which documentation *does* help (e.g., when source is unavailable or models are weaker).

## Connections to Other Work
This challenges assumptions implicit in [[In-Context Learning]] and [[Retrieval-Augmented Generation (RAG)]] for code tasks. It relates to broader questions in [[large-language-models]] about when additional context helps versus hurts (context bloat, noise). The paper echoes findings in mechanistic interpretability showing that models sometimes ignore or misuse auxiliary information. It also connects to the broader literature on [[code generation]] and [[software engineering]] applications of LLMs, which often assume richer context improves outcomes.

## Practical Applications
1. **Bug-fix automation tools**: Real-world evidence that agent-based issue resolution works without expensive documentation — reducing the overhead for open-source projects adopting automated triage.
2. **Legacy code modernization**: When refactoring old codebases, the finding suggests agents don't need perfect documentation to understand intent, lowering barriers to adoption.
3. **Minimal-context code search**: For teams with poor documentation, the result is reassuring — agents can still assist without first investing in documentation improvement.

## Product & Startup Ideas
1. **CodeAssistant Pro**: A GitHub bot that auto-resolves issues using just issue text + code diffs, marketed on the insight that documentation overhead is unnecessary. Charge per resolved issue.
2. **DocOptimizer SaaS**: Tools for teams to measure whether their documentation is actually useful to AI agents (using the roundtrip benchmark), and identify which files need better descriptions.
3. **Undocumented Code Intelligence**: A VS Code extension that warns developers when they're reviewing undocumented code, but surfaces the insight that agent-based fixes don't require it — reframing documentation as human-facing, not AI-facing.
4. **Repository Health Scanner**: Analyze GitHub repos to identify code sections where documentation is missing but agents could still help, and prioritize where to add it for *human* readers.
5. **Lightweight API Docs Generator**: Auto-generate minimal API documentation optimized for agent readability, not human readability — much shorter, completeness-driven rather than narrative.

## Technical Limitations
1. **Limited to Python/specific domains**: The benchmark and optimizer were evaluated on a narrow set of repositories; generalization to other languages or domains is unclear.
2. **Test coverage assumption**: The roundtrip benchmark requires comprehensive tests. Code without good test suites cannot be evaluated fairly.
3. **Issue selection bias**: The ten repositories chosen may not represent the diversity of real-world codebases (different languages, maturity, test quality, issue complexity).
4. **Model-specific findings**: Results are tied to specific model families (e.g., GPT-based). Smaller or differently-trained models might benefit from documentation.
5. **Source availability assumption**: The negative result assumes source code is present and retrievable. In closed-source or distributed systems, documentation might help more.
6. **Shallow optimization signal**: The optimizer may overfit to the benchmark; there could be other aspects of documentation quality (e.g., maintainability, teaching value) not captured.

## Open Questions
1. **Why doesn't documentation help?** Is it that models are already implicitly learning code semantics from context, or does additional text introduce noise? Mechanistic analysis could reveal what agents actually use.
2. **Domain-dependent transfer**: Do results hold for more complex domains (e.g., ML frameworks, distributed systems)? Are there issue types where documentation *does* help?
3. **Weak model regime**: How do results change with smaller or weaker models? Does the benefit of documentation emerge only at scale?
4. **Hybrid approaches**: Could smarter context selection (e.g., embedding-based retrieval of relevant doc snippets) beat naive static documentation?
5. **Human-AI interaction**: Even if agents don't benefit, do humans assisted by agents benefit from documentation? (Different research question, but practical.)
6. **Fine-tuning**: Can documentation improve performance if agents are fine-tuned on code-to-description pairs, rather than just prompted?

## Key Takeaway
Better code documentation doesn't actually help AI agents fix bugs when source code is available—they solve issues just as well without it.
