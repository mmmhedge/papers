# Universal Byte-Level Encoding: UTF-8/UTF-16 Routing to Reduce Cross-Script Token-Budget Disparities

**Authors:** Hyunsik Kim, Youngmoon Jung
**Published:** 2026-10-01 | **arXiv:** [2610.01984v1](http://arxiv.org/abs/2610.01984v1)

## Summary
This paper addresses a fairness problem in multilingual language models: non-English scripts require more tokens to represent the same information because their characters are encoded inefficiently. The authors propose Universal Byte-Level Encoding (UBE), a tokenization method that selectively routes characters through different Unicode encoding schemes (UTF-8 vs UTF-16) to equalize token costs across languages while preserving efficiency for English.

## Theoretical Background
Byte-pair encoding (BPE) is the standard tokenization algorithm for modern language models — it starts with raw bytes and iteratively merges the most frequent adjacent byte pairs into new tokens. Multilingual models use byte-level BPE (BBPE) because it can theoretically handle any Unicode text without a fixed vocabulary limit. However, UTF-8 encoding (the dominant Unicode standard) represents characters as variable-length byte sequences: English uses 1 byte per character, many European languages use 2 bytes, and many Asian scripts use 3-4 bytes. This creates an "encoding floor" — the minimum token cost even before learned merges are applied. A character requiring 4 bytes starts at a disadvantage compared to a 1-byte English character, inflating token counts for certain scripts.

## Core Contributions
1. **Identifies and quantifies the encoding floor problem**: Formalizes how UTF-8's variable-length encoding creates cross-script token-budget disparities, with concrete measurements across Unicode scripts.
2. **Proposes UBE's dual-alphabet routing**: Routes 1-2 byte UTF-8 characters normally, but switches 3-4 byte UTF-8 characters through UTF-16 representation before BPE. This reduces the pre-merge cost for affected characters without degrading English efficiency.
3. **Proves exact Unicode compliance**: Validates that UBE exactly round-trips all Unicode scalar values and passes official Unicode normalization, grapheme-break, and emoji test suites.
4. **Demonstrates empirical gains**: Shows reduced token-count dispersion across languages, maintained language model quality, and practical benefits (more usable context, faster processing) on multilingual benchmarks.

## Connections to Other Work
This work relates to broader research in [[tokenization]] for multilingual NLP and fair representation of diverse languages in [[large-language-models]]. It sits between pure byte-level approaches (inefficient but universal) and fixed-vocabulary subword tokenization (efficient but limited to pre-defined languages). The paper implicitly engages with discussions about [[alignment]] — not in the safety sense, but in the alignment of token budgets across linguistic groups. Prior work on multilingual model fairness and morphology-aware tokenization provides context, though this paper's byte-routing approach is novel.

## Practical Applications
1. **Improved multilingual LLM deployment**: Reducing token counts for high-premium scripts directly lowers inference cost and latency for models serving non-English users, making deployment more economical in price-sensitive regions.
2. **Fair context length allocation**: Users querying in CJK, Arabic, or other 3-4 byte scripts now get proportionally similar context windows as English users without changing model architecture.
3. **Faster prompt processing**: Content-matched benchmarks show speed improvements, especially valuable for real-time applications (chat, search, translation) handling mixed-language input.
4. **Reduced memory and API costs**: Fewer tokens per request means lower memory requirements during inference and cheaper per-call costs for API providers, benefiting both large-scale deployments and fine-tuning workflows.

## Technical Limitations
1. **Modest absolute gains**: While UBE reduces dispersion, the improvements are incremental — token counts for 3-4 byte scripts remain higher than English, just less unfairly so. This is a fairness fix, not a silver bullet.
2. **UTF-16 routing overhead**: Switching encoding schemes adds computational overhead during tokenization; the paper doesn't deeply analyze latency costs at scale or cache invalidation patterns.
3. **Limited scope to BMP**: The optimization targets 3-byte Basic Multilingual Plane characters; emoji and rare scripts outside BMP may not benefit equally, and the fix doesn't scale to hypothetical 5+ byte sequences.
4. **Compatibility and tooling**: Existing tokenizer implementations, training pipelines, and inference engines are built around UTF-8. Adopting UBE requires updates across the stack; the paper doesn't quantify migration costs.
5. **Language-specific exceptions**: Scripts with unusual properties (combining marks, right-to-left, complex graphemes) may not benefit uniformly from the byte-routing heuristic; per-language tuning might be needed.

## Open Questions
1. **Can UBE be optimized further?** Are there other encoding schemes (e.g., UTF-32 subsets) or routing strategies that yield better compression for specific script families?
2. **How does UBE interact with subword morphology?** The paper mentions composability with morphology-based tokenization, but does it degrade the benefits of morphological analysis for agglutinative languages?
3. **What is the end-to-end latency cost?** Detailed benchmarks of tokenization speed, cache miss rates, and decoding overhead compared to standard BBPE would help practitioners assess real deployment costs.
4. **Does fairness improve downstream task performance?** If non-English scripts now fit more tokens in context, do multilingual models train/reason better on those languages, or is the benefit purely computational?
5. **Can this apply to very-long-context models?** As context lengths grow (100K+ tokens), does the relative benefit of UBE increase, and are there new trade-offs with caching or retrieval-augmented generation?

## Key Takeaway
UBE routes different byte ranges through different encodings to equalize token costs across languages without hurting English efficiency.
