# CoTrace: Data Recipes for Training Terminal Agents with Harness-Model Co-Evolution

**Authors:** Jixuan Chen, Jiaxin Zhang, Qinyuan Ye, Yada Pruksachatkun, Haoxiang Zhang et al.
**Published:** 2026-10-07 | **arXiv:** [2610.10426v1](http://arxiv.org/abs/2610.10426v1)

## Summary
This paper addresses how to train AI agents (models that interact with tools and environments) by treating the model and its runtime "harness" (prompt formatting, tool binding, error handling) as co-evolving components. The key insight: trajectories collected during training are only valuable for a given harness, yet prior work treats them interchangeably. CoTrace is a data-routing system that ensures trajectories are matched to the harness that generated them, improving performance from 78 to 90 solved tasks on a benchmark while using smaller, more efficient training data.

## Theoretical Background
Terminal agents — language models that execute multi-step commands by calling external tools and interpreting results — have emerged as a paradigm beyond pure text generation. Their success depends on two coupled systems: (1) the model's learned policy (how to decide what action to take), and (2) the harness (the formatting and error-recovery wrapper that translates model outputs into valid tool calls). Prior work on co-evolution frameworks has attempted to improve both simultaneously, but typically pooled training trajectories without accounting for harness-dependence. The paper builds on supervised fine-tuning (SFT) and reinforcement learning (RL) training paradigms, introducing the concept that trajectory provenance — which harness produced a rollout — must be tracked and respected during downstream training.

## Core Contributions
1. **Harness-aware data routing**: Explicit framework recognizing that a trajectory's training value is conditional on the harness that generated it; trajectories from incompatible harnesses introduce distribution shift.
2. **CoTrace methodology**: A three-component data recipe — trajectory routing (matching rollouts to their source harness), provenance tracking, and curriculum refresh — that decouples harness search from policy training via component-wise promotion decisions.
3. **Empirical efficiency gain**: Demonstrated that a smaller corpus of harness-matched data produces larger model improvements than much larger pooled corpora at lower computational cost.
4. **Transfer robustness insight**: Showed that out-of-distribution generalization failures are fundamentally rooted in harness mismatch; maintaining consistency between training and evaluation runtimes prevents procedural breakdowns.

## Connections to Other Work
This work extends [[co-evolution]] approaches in agent training and relates conceptually to [[curriculum learning]] (selective ordering of training data) and [[data-centric AI]] (viewing data quality as paramount). It connects to broader [[reinforcement-learning]] literature on trajectory reuse and importance sampling, but shifts focus to the structural interface between model and execution environment rather than pure policy optimization. The emphasis on runtime consistency echoes concerns in [[domain adaptation]] and [[distribution shift]] in machine learning, but applied to the underexplored axis of harness compatibility.

## Practical Applications
1. **Autonomous code execution systems** (e.g., GitHub Copilot, SWE agents): Improved reliability by ensuring training data harnesses match production scaffolds, reducing silent failures.
2. **Business process automation**: Terminal agents calling internal APIs; harness-aware training ensures agents work correctly with the actual API binding and error-handling layers they'll encounter in production.
3. **Robotic task execution**: Where the harness encodes sensor preprocessing and actuation constraints; matching training harness to deployment harness prevents sim-to-real friction.
4. **Multi-tool LLM assistants**: Systems like Claude or ChatGPT that invoke plugins; CoTrace principles ensure plugin-calling behavior learned on one scaffolding doesn't break when the plugin interface changes.

## Product & Startup Ideas
1. **"HarnessOps" platform**: A data management and training orchestration tool for teams building terminal agents, tracking harness provenance automatically and flagging training-evaluation mismatches before deployment.
2. **Harness-agnostic model fine-tuning service**: Managed SaaS that applies CoTrace internally, allowing customers to submit model + harness pairs and receive optimized checkpoints without manual trajectory curation.
3. **Automated agent testing & validation**: Tool that generates harness-matched synthetic data by co-evolving test harnesses with model checkpoints, surfacing failure modes early.
4. **"Harness Compatibility Checker"**: Lightweight library integrated into CI/CD that audits training data against deployment harness versions, warning when skew is detected.
5. **Enterprise agent marketplace**: Platform for sharing pre-trained terminal agents with versioned harnesses, ensuring downstream users inherit the correct harness-model pairing from training.

## Technical Limitations
1. **Scalability of provenance tracking**: In large-scale distributed training, maintaining tight correspondence between trajectories and specific harness versions introduces overhead and complexity; the paper doesn't address distributed systems challenges.
2. **Harness design responsibility**: The method assumes harnesses are well-designed; poor harness design or missing error-recovery logic upstream will propagate downstream. No principled approach to harness architecture is offered.
3. **Cold-start harness synthesis**: Early-stage harness search (before trajectories are available) still relies on prior heuristics; the paper doesn't fully solve the chicken-egg problem of bootstrapping.
4. **Generalization within harness families**: If multiple harnesses are valid (e.g., different prompt formats for the same tool), it's unclear whether a model trained on one harness transfers to another in the same family, or if retraining is always required.
5. **Compute cost of component-wise promotion**: The alternating decoupled framework may require more model evaluations than unified co-evolution; actual wall-clock comparison is not provided.

## Open Questions
1. How much harness drift (incremental changes to error handling, prompting) can a trained policy tolerate before retraining becomes necessary?
2. Can meta-learning or hypernetwork approaches learn a *harness-agnostic* policy that adapts to harness changes at test time without retraining?
3. Does curriculum ordering within harness-matched data (beyond just matching) further improve sample efficiency?
4. How do the results scale to multi-agent scenarios where different agents use different harnesses; can knowledge transfer between harnesses improve overall performance?
5. What is the theoretical relationship between harness complexity (number of tools, error types) and the amount of matched data needed for convergence?

## Key Takeaway
Matching training trajectories to their source runtime harness yields dramatic efficiency gains; harness-model consistency is as critical as model quality itself.
