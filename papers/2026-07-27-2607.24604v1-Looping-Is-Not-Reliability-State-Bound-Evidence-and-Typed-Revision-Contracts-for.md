# Looping Is Not Reliability: State-Bound Evidence and Typed Revision Contracts for Agentic Code Repair

**Authors:** Xueping Gao, Jianwei Yang, Qiang Yang
**Published:** 2026-07-27 | **arXiv:** [2607.24604v1](http://arxiv.org/abs/2607.24604v1)

## Summary
This paper challenges the assumption that looping—repeatedly generating, testing, and revising code—automatically improves reliability in code repair agents. The authors conduct rigorous empirical studies on HumanEval bugs, showing that repeated revisions can actually degrade correctness despite theoretical "ever-correct" guarantees, and propose a formal contract system that separates concerns like verification, state preservation, and auditing to ensure agentic code repair is actually reliable.

## Theoretical Background
Code repair using language models typically follows a generate-test-revise (GTR) loop: an agent produces a patch, tests it, and if it fails, tries again. This resembles [[reinforcement-learning]] iteration but without explicit rewards. The paper builds on work in [[agents]] and tool-using LLMs, where models interact with external environments (code executors). Key frameworks include program synthesis (generating code that satisfies specs) and formal verification (mathematically proving correctness). The authors also draw on causal inference methods—particularly "frozen programs" and risk-set bias removal—to isolate whether improvements come from agent behavior or confounding factors like trace staleness.

## Core Contributions
1. **Empirical paradox**: Shows that under forced revision, measured correctness drops from 82% after one revision to 67% after two, despite "ever-correct" (has anyone seen a correct patch?) rising to 84.7%—revealing a measurement-reality gap.
2. **State-bound evidence**: Demonstrates that using stale (outdated) execution traces harms repair by 22.2 percentage points versus current traces, using causal study designs to eliminate selection bias.
3. **Typed revision contract**: Derives a formal specification separating five concerns—admission (when to start revision), preservation (keeping verified checkpoints), grounded certification (tying evidence to exact code states), competence (agent ability), and liveness (termination)—rather than treating looping as monolithic.
4. **Reference implementation**: Builds a mechanically enforceable subset with auditable receipts, treating it as an executable specification rather than claiming improved repair performance.

## Connections to Other Work
This relates to [[RLHF]] and tool-use in LLMs by questioning implicit assumptions about iteration. It connects to formal methods and contract-based programming (e.g., Design by Contract) applied to agentic systems. The causal inference methods (frozen programs, risk-set adjustment) parallel work in [[mechanistic-interpretability]] on isolating causal effects. The finding that "looping ≠ reliability" complements critiques of test-driven agentic loops in [[agents]] and [[alignment]] (e.g., reward hacking via measurement gaps).

## Practical Applications
1. **Code review assistants**: Instead of blindly resubmitting patches, systems now preserve only verified checkpoints and flag when traces become stale.
2. **Bug bounty automation**: Organizations running autonomous repair on public codebases can audit why patches were submitted (via admission receipts), reducing liability.
3. **CI/CD integration**: Continuous integration pipelines can enforce the typed contract to prevent agents from getting stuck in futile revision loops.
4. **Certification in high-stakes domains**: Safety-critical systems (aerospace, finance) can verify not just that a patch passes tests, but that the agent followed a sound revision strategy with auditable state bindings.

## Technical Limitations
1. **Limited scope**: Studies use small benchmarks (HumanEval, 24 repository bugs); generalization to industrial codebases with complex dependencies is unclear.
2. **No competence improvement**: The paper *explicitly* does not claim the contract improves repair success—only that it makes existing behavior more reliable and auditable.
3. **Verifier dependence not calibrated**: The contract assumes an external test oracle (unit tests, type checkers) exists and is trustworthy; how to handle weak or adversarial oracles is unaddressed.
4. **Stale trace harm is context-specific**: The 22.2-point penalty for stale traces comes from a specific setup (14B model); effect sizes may vary with model scale, domain, or trace age.
5. **Floor effects in repository experiments**: Four coder stacks showed heterogeneous results with no statistically significant improvements, suggesting the contract may not generalize uniformly.

## Open Questions
1. **Scaling**: Do the causal findings (stale trace harm) replicate on larger, more diverse code repair tasks and model scales?
2. **Verifier calibration**: Can we formally quantify when a verifier is "trustworthy enough" for the contract to provide safety guarantees?
3. **Competence interaction**: Does the contract improve repair when combined with better agents or fine-tuned verifiers, or is improvement orthogonal?
4. **Loop termination**: What principled stopping criteria prevent infinite revision? Can we derive them from the contract?
5. **Multi-agent revision**: How should the contract evolve when multiple agents collaborate on repair, or when an agent can call human reviewers?

## Key Takeaway
Repeating code revisions doesn't guarantee reliability—proper state tracking, evidence binding, and verification auditing do.
