# Requirement-Bound Verified Commissioning: A Frozen Four-Billion-Parameter Local Model as a Candidate Generator under an External Acceptance Layer with Verification and Release Authority

**Authors:** Mehmet Iscan
**Published:** 2026-09-24 | **arXiv:** [2609.30219v1](http://arxiv.org/abs/2609.30219v1)

## Summary
This paper develops a safety protocol for automated systems that generate plans by separating candidate generation from release decisions. A frozen 4-billion-parameter language model proposes candidates, but a deterministic external gate (based on formal grammar) must verify and approve before release. The approach achieved zero false releases on 83 benchmark tasks, though performance degrades significantly on out-of-distribution cases.

## Theoretical Background
The work builds on [[RLHF]]-era concerns about controlling language model outputs through external verification layers rather than relying solely on model training. It combines formal methods (deterministic parsing and sealed grammars) with neural generation — a hybrid approach similar to neurosymbolic AI. The acceptance protocol draws from systems engineering verification practices, where independent layers must approve decisions before deployment. The authors employ statistical validation via Clopper-Pearson confidence bounds, a classical technique for estimating error rates under strict operational constraints.

## Core Contributions
1. **Separation of concerns**: Decoupling candidate generation (LM) from release authority (external gate), allowing independent measurement of each component's failure modes.
2. **Verification under sealed constraints**: A deterministic grammar acts as a gatekeeper; plans pass only if both derived facts can be proven within the formal system.
3. **Calibrated uncertainty handling**: When a task cannot be solved deterministically, the system routes it to the LM rather than failing silently — but only the LM's output is released if the gate approves.
4. **Quantified safety bounds**: Achieved 0% false release rate on 83 benchmark cases with statistical upper bound (3.54% at 95% confidence), though this bound does not hold out-of-distribution.

## Connections to Other Work
This relates to [[alignment]] efforts in LLM deployment, particularly ideas around interpretability-based controls and external constraint enforcement. It echoes work on verifiable AI systems and formal methods for neural network validation. The approach shares spirit with constitutional AI and rule-based filtering layers, but uses explicit formal grammar rather than learned values. The failure modes (e.g., coordinate exclusion, incorrect user answers being propagated) highlight challenges similar to those in [[mechanistic-interpretability]] — understanding when and why models fail despite external gates.

## Practical Applications
- **Robotic commissioning and sensor calibration**: Automating setup of mechatronic systems where incorrect bindings (sensor-to-coordinate mapping) could damage equipment or compromise safety.
- **Control system configuration**: Industrial systems requiring verified sensor-actuator alignment before runtime.
- **Medical device setup protocols**: Where parameter binding errors could affect patient safety; the gate prevents unapproved configurations from reaching operators.
- **Autonomous vehicle parameter tuning**: Verifying sensor calibration proposals before deployment.

## Product & Startup Ideas

2. **SafeAI-for-Robotics**: Middleware that intercepts robotic control commands, routes ambiguous cases to an LM, but only executes after formal verification — targeted at manufacturers integrating collaborative robots.
3. **Verifiable Configuration as a Service**: API that takes system requirements (sensor specs, wiring diagrams) and returns formally verified configuration plans, logging all LM proposals and gate decisions for compliance.
4. **Fault-Tolerant LM Deployment Framework**: Open-source toolkit for teams to wrap any LM with external verification layers, enabling safer deployment of generative models in regulated industries.

## Technical Limitations
- **Out-of-distribution brittleness**: The 3.54% error bound (on 83 benchmark tasks) does not hold for 146 new tasks; one false release occurred at seed 0, violating the sealed 5% threshold.
- **Eligibility oracle leak**: The protocol requires knowing the "gold standard answer" upfront to decide whether to query the user — this creates a circular dependency; real deployment cannot use this decision rule without access to answers.
- **User answer robustness not tested**: The system fails when users provide incorrect answers (169 of 431 failures on answerable tasks); no policy for detecting or handling unreliable user input was evaluated.
- **Limited model capacity**: Using a 4B parameter frozen model may undersupply the reasoning needed for complex commissioning scenarios.
- **Sealed grammar brittleness**: If the formal grammar does not capture legitimate requirements, tasks are incorrectly routed to the LM, and gate verification may reject valid plans.
- **No interactive refinement**: The protocol does not support iterative dialogue to resolve ambiguous task descriptions.

## Open Questions
- **Can the out-of-distribution error bound be tightened?** What causes the jump from 0/83 to ≥1/146 errors, and how can the gate be made more robust to unseen task distributions?
- **How should the system decide when to query a user without access to answer keys?** A practical eligibility criterion (not oracle-based) is needed for deployment.
- **What is the cost-benefit of user involvement?** If 169 of 431 user answers lead to incorrect releases, is human-in-the-loop worth the overhead?
- **Can the gate learn or adapt?** The frozen model + sealed grammar may be too rigid; could the gate use feedback from successful/failed deployments?
- **How does performance scale to multi-step plans?** All 144 benchmark tasks appear to be single-decision problems; commissioning real systems often involves sequences of interdependent decisions.
- **What happens with adversarial or out-of-scope inputs?** Is the gate robust to users or agents who deliberately try to bypass it?

## Key Takeaway
External verification gates can catch LM mistakes, but only work reliably on training-like tasks — real deployment requires robust handling of user errors and out-of-distribution cases.
