# Long Text to Predictive Features: LLM-Guided Blockwise Feature Engineering via Executable Program Search

**Authors:** Ziming Dai, Dabiao Ma, Ziheng Guo, Jack Dong, Zimu Zhou
**Published:** 2026-10-08 | **arXiv:** [2610.12390v1](http://arxiv.org/abs/2610.12390v1)

## Summary
This paper addresses a practical problem: financial risk systems have valuable information trapped in long text documents, but running a language model on every prediction in real-time is too slow and expensive. The authors propose LLM-BlockFE, which uses an LLM offline to design feature-extraction programs from text, then freezes these programs for fast deployment. The system searches for good feature combinations intelligently, avoiding greedy dead-ends, and shows real-world improvements in deployed financial applications.

## Theoretical Background
The paper builds on two established areas. First, feature engineering — the manual process of transforming raw data into useful signals for machine learning models — is foundational to predictive systems, especially in finance where domain expertise matters. Second, large language models (LLMs — neural networks trained on vast text to generate or analyze language) have recently proven capable of reasoning about code and data transformations. The authors combine these by letting an LLM propose feature programs (executable code that extracts patterns from text), then use a search algorithm to find the best combinations without calling the LLM repeatedly at inference time.

## Core Contributions
1. **LLM-BlockFE framework**: A method to generate executable feature programs from long text offline, avoiding expensive LLM inference during deployment.
2. **Block-level rollback mechanism**: Instead of greedy search (which commits to choices irreversibly), the algorithm can backtrack using "depth-calibrated credit allocation" — a principled way to decide which past decisions were mistakes.
3. **Interleaved multi-trajectory search**: Multiple independent search paths explore the feature space in parallel while sharing information about each path's direction, reducing wasted exploration.
4. **Empirical validation on financial data**: Demonstrates 0.69–3.58 percentage point AUC improvements in benchmarks and 0.02–1.56 percentage point KS improvements (a key risk metric) in live deployed systems.

## Connections to Other Work
This work sits at the intersection of [[RLHF]]-style use of LLMs as reasoning engines, program synthesis (using models to generate executable code), and automated machine learning (AutoML). It differs from naive approaches that call an LLM at inference time (slow, expensive) and from purely manual feature engineering (labor-intensive, non-scalable). The search strategy with rollback resembles hierarchical reinforcement learning or best-first search with learned heuristics, though adapted for the feature-program domain. Related to [[neural architecture search]] but applied to feature programs rather than model architectures.

## Practical Applications
1. **Real-time fraud detection in banking**: Extract risk signals from transaction descriptions, customer notes, or email communications without running an LLM per transaction.
2. **Loan origination risk**: Convert applicant narratives (employment history, loan purpose, explanations) into fast, scored features for approval decisions.
3. **Insurance underwriting**: Parse claim descriptions or policy application text into structured risk indicators for premium pricing.
4. **Compliance monitoring**: Extract compliance-relevant features from internal communications or regulatory filings for automated flagging.
5. **Credit decisioning**: Convert borrower profiles (written histories, statements) into numerical risk scores that can be evaluated in milliseconds.

## Product & Startup Ideas
1. **AutoFE-for-Finance SaaS**: A platform where financial institutions upload their raw text datasets and unstructured logs, click a button, and receive optimized feature programs tailored to their prediction tasks (churn, fraud, default risk). Subscription pricing based on dataset volume and number of deployed models.
2. **Compliance Feature Store**: Pre-built library of feature programs for regulatory text (10-Ks, meeting transcripts, internal memos) that enterprises can license and customize for their specific compliance and risk thresholds.
3. **Real-time Risk API**: A service that accepts long-form customer/transaction text and returns risk scores in <100ms using pre-trained frozen feature programs, bundled with update services as regulations evolve.
4. **Feature-as-Code marketplace**: A GitHub-style platform where data scientists publish vetted feature programs for common text sources (news, earnings calls, regulatory filings, customer reviews), with version control and performance leaderboards.
5. **LLM-to-Production workflow tool**: IDE and deployment platform specifically for converting LLM-generated feature ideas into frozen, auditable, production-grade code, with A/B testing and drift monitoring built in.

## Technical Limitations
1. **Text quality assumptions**: The method assumes long text contains signal; if text is noisy, sparse, or domain-misaligned, feature programs may not help.
2. **Frozen programs become stale**: Once deployed, feature programs don't adapt to distribution shift or language evolution; retraining requires offline work.
3. **Dependence on LLM quality**: The initial feature proposals come from an LLM; poor LLM design or prompting limits the program diversity the search can explore.
4. **Scalability of search**: The interleaved multi-trajectory search may become computationally expensive on very large feature spaces; no analysis of computational cost scaling.
5. **Interpretability tradeoff**: While faster than real-time LLM calls, the learned feature programs may still be opaque; no discussion of how to explain why a program chose a feature.
6. **Limited baseline comparisons**: Compared mainly against manual engineering and direct LLM approaches; unclear how it fares against other AutoML or program-synthesis methods.

## Open Questions
1. How does performance degrade as the original LLM degrades in quality or relevance (e.g., model becomes outdated, domain shift)?
2. Can the method be extended to handle multiple text fields or hierarchical text structures (e.g., nested documents)?
3. What is the sensitivity to the search hyperparameters (trajectory count, rollback threshold, sharing mechanism)? Is there principled guidance for tuning?
4. How do you detect and quantify distribution shift in the frozen programs post-deployment, and what's the cost/timeline for retraining?
5. Can you extract explicit explanations or rules from the final feature programs, making them more interpretable for regulators?
6. Does the method work for other unstructured modalities (images, audio) or is it text-specific?

## Key Takeaway
LLM-guided feature search converts long text into fast, deployable feature programs, avoiding expensive real-time LLM calls while improving financial risk predictions.
