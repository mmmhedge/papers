# Engineering Sustainable Agents: A Systematic Comparison of Agentic LLMs for Developer Workflows

**Authors:** Merve Astekin, Yan Naing Tun, Arda Goknil, Erik Johannes Husom, Lwin Khin Shar et al.
**Published:** 2026-10-02 | **arXiv:** [2610.03010v1](http://arxiv.org/abs/2610.03010v1)

## Summary
This paper systematically evaluates agentic LLM systems (where multiple AI agents collaborate) versus simpler single-model approaches across five software engineering tasks. The key finding: multi-agent designs consume 6–7× more energy and time while delivering inconsistent accuracy gains, challenging the assumption that more complex agent coordination always improves performance.

## Theoretical Background
The paper builds on two converging trends: (1) LLMs as coding assistants, where models like GPT and open-weight alternatives are fine-tuned for software tasks, and (2) multi-agent systems — architectures where independent agents coordinate to solve complex problems. The authors compare these approaches against a non-agentic baseline (a single LLM query) using standard SE metrics (accuracy, latency, energy). Their evaluation spans six open-weight models on three hardware platforms, treating the LLM-based agent as a computational entity with measurable resource costs, not just task performance.

## Core Contributions
1. **Systematic empirical comparison** of agentic vs. non-agentic LLM configurations across five realistic SE tasks (code generation, technical debt ID, vulnerability detection, log parsing/analysis).
2. **Quantified trade-offs**: Multi-agent workflows consume 6.36× more energy and run 6.07× slower on average; worst-case slowdowns reach 160× for specific task–hardware pairs.
3. **Pareto-front analysis**: 59 of 66 Pareto-optimal (best trade-offs between accuracy and resources) configurations use lightweight or single-agent setups, not multi-agent designs.
4. **Task-dependent optimization levers**: Model choice and prompt strategy are not universal; their effectiveness varies per task, requiring bespoke tuning rather than global defaults.
5. **Actionable design guidelines** for sustainable, resource-aware LLM-based developer tools.

## Connections to Other Work
This work directly challenges the narrative of increasingly complex agent orchestration (see [[multi-agent-systems]], [[agents]]) and aligns with growing concerns about the environmental cost of [[large-language-models]]. It relates to RLHF and prompt engineering literature (which optimize accuracy without resource constraints) but extends those to include latency and energy. The Pareto-front framing echoes multi-objective optimization in AutoML but applies it to software engineering tasks. It also bridges [[generative-models]] efficiency work and the emerging field of sustainable AI.

## Practical Applications
1. **Developer IDE plugins**: VS Code, JetBrains extensions that choose lightweight single-agent configs for real-time code completion to avoid latency penalties on local hardware.
2. **On-device code tools**: Enterprises running LLM-based code assistants locally (privacy + cost) can use these guidelines to select non-agentic or minimal-agent designs.
3. **Log analysis platforms**: DevOps/SRE teams can deploy lightweight single-model log parsers instead of multi-agent pipelines, reducing cloud compute spend.
4. **Vulnerability scanning as a CI/CD step**: Security teams embedding LLM vulnerability detection into build pipelines can avoid multi-agent overhead by selecting task-optimized single-agent or non-agentic configs.
5. **Technical debt metrics**: Automated code review systems balancing accuracy (multi-agent advantage for some tasks) against infrastructure cost via the paper's Pareto front.

## Product & Startup Ideas
1. **LLM Config Optimizer**: A SaaS tool that profiles a company's developer workflows, measures energy/latency costs of different LLM configurations, and auto-selects Pareto-optimal settings per task (code gen vs. security scan).
2. **Sustainable AI Consulting**: Advise enterprises migrating to LLM-based dev tools on which agent architectures minimize energy and carbon footprint while meeting accuracy SLAs.
3. **Lightweight Code Agent Framework**: Open-source library providing pre-optimized, single-agent or non-agentic LLM configs for common SE tasks (tested on Raspberry Pi, M-series chips, cloud VMs).
4. **Green Code Review Platform**: A specialized code review tool using lightweight, non-agentic LLM configs optimized for vulnerability and debt detection; market as "the energy-efficient alternative to multi-agent approaches."
5. **FinOps for AI**: Billing and usage monitoring for in-house LLM-based development tools, surfacing energy and latency costs per task and recommending Pareto-optimal config switches based on this paper's findings.

## Technical Limitations
1. **Limited task scope**: Five tasks are sampled; results may not generalize to other SE tasks (e.g., architectural design, natural-language requirements parsing).
2. **Hardware diversity**: Tested on three platforms; edge devices, specialized accelerators (TPUs, custom silicon), or cloud GPUs may show different Pareto trade-offs.
3. **Model selection**: Six open-weight models tested; proprietary APIs (OpenAI, Anthropic) may have different energy/accuracy profiles not captured.
4. **Prompt engineering ceiling**: Assumes simple prompt strategies; sophisticated chain-of-thought or in-context learning might shift Pareto fronts but are not exhaustively explored.
5. **Agent design space**: The study compares simple multi-agent designs; more sophisticated coordination (hierarchical planning, learned routing) might achieve better trade-offs but are outside scope.
6. **Accuracy metric bias**: Tasks vary in how they define correctness; vulnerability detection and log parsing may be inherently easier to parallelize than code generation.

## Open Questions
1. Do more sophisticated prompt strategies (e.g., chain-of-thought, tree-of-thought) shift the Pareto front for multi-agent systems, or do they amplify energy costs further?
2. Can learned routing or dynamic agent selection (e.g., routing queries to lightweight or heavyweight models based on input) beat static Pareto-optimal configs?
3. How do results change for longer-horizon tasks (e.g., multi-file refactoring, architectural design) where agent coordination might be more critical?
4. What is the carbon footprint of *training* multi-agent LLM systems vs. inference? Does that change the sustainability calculus?
5. Can distillation or quantization of open-weight models recover multi-agent accuracy gains with non-agentic energy costs?
6. How do human developers perceive latency and energy trade-offs? Is a 6× slowdown acceptable if accuracy improves 5%? User studies needed.

## Key Takeaway
Multi-agent LLM designs cost 6–7× more energy with inconsistent accuracy gains; simpler single-agent or non-agentic approaches dominate practical trade-offs for developer workflows.
