# How to Loop MoE: Flatten the Experts, Untie the Attention

**Authors:** Shouren Wang, Chuang Ma, Mohsen Hariri, Debargha Ganguly, Wang Yang et al.
**Published:** 2026-09-28 | **arXiv:** [2609.35751v1](http://arxiv.org/abs/2609.35751v1)

## Summary
This paper proposes Foil, a method for designing mixture-of-experts (MoE) models that reuse layers multiple times ("looping") to improve computational efficiency. The key insight is to flatten the expert structure — halving expert layers while doubling experts per layer — and give each loop pass its own attention parameters. The approach achieves better pretraining loss and downstream performance at the same parameter and compute budgets.

## Theoretical Background
The paper builds on two separate architectural trends in large language models:

**Looped Transformers** reuse the same block of transformer layers multiple times during forward passes. This allows a fixed-size model to spend extra computation refining its representations, theoretically making fuller use of parameters without increasing model size.

**Mixture-of-Experts (MoE)** models activate only a small subset of "expert" neural networks for each input token, controlled by a learned routing function. This reduces per-token compute while maintaining large parameter counts. Standard MoE models face challenges like load imbalance (some experts used frequently, others rarely) and underutilized capacity.

The paper's novelty is combining these two paradigms — applying looping specifically to MoE architectures — which raises a fundamental design question: when you loop an MoE, how should you structure the experts and attention across passes?

## Core Contributions

1. **Foil architecture design**: A concrete answer to looping MoE via (1) flattening — reorganizing experts so each loop pass routes through a larger, shallower expert pool, and (2) untying attention — giving each pass independent attention parameters while keeping experts and routers shared across passes.

2. **Empirical validation**: Demonstrates that flattened looped MoE consistently outperforms unflattened baselines on pretraining loss (0.012 nat improvement at 100B tokens) with equal parameters and compute, and maintains or improves downstream task accuracy.

3. **Routing dynamics analysis**: Shows that routing confidence (how certain the router is) is a better indicator of healthy expert use than load balance metrics, and that untying attention improves both routing confidence and load balance.

4. **Design principles for sparse looped MoE**: Through ablations, derives practical guidance — looping and widening expert layers have amplifying returns, and looped MoE should prefer more experts per layer and more passes.

## Connections to Other Work

This work bridges [[Looped Transformers]] (parameter reuse for efficiency) and [[Mixture-of-Experts]] (sparse conditional computation). It addresses known MoE challenges around load balancing and expert utilization, which have been explored in prior work on router design and auxiliary losses. The routing confidence metric relates to work on interpretability in conditional computation models. The flattening strategy parallels architectural innovations in [[Vision Transformers]] and other domains where depth-to-width tradeoffs are explored.

## Practical Applications

1. **Efficient large language model training**: Reduce wall-clock training time and memory for models at fixed parameter budgets, critical for labs with constrained compute.

2. **Mobile and edge deployment**: The same parameter count with better quality enables smaller models for on-device inference.

3. **Long-context models**: More efficient compute per token could allow longer sequence processing in production systems.

4. **Cost-optimized inference serving**: Better loss-to-compute tradeoffs directly reduce inference cost for commercial LLM APIs.

## Product & Startup Ideas

1. **MoE architecture search service**: A cloud tool that auto-tunes looping, flattening, and attention-tying for a given compute/parameter budget and downstream task, selling to ML teams optimizing model efficiency.

2. **Inference optimization SaaS**: Package Foil-style models as pre-trained checkpoints on a model hub, letting companies deploy cheaper-to-run LLMs without retraining.

3. **Hardware-aware MoE compiler**: Tools that automatically translate Foil designs into efficient inference code for specific hardware (TPUs, GPUs, custom accelerators).

4. **Open-source efficient LLM suite**: Release pre-trained Foil models at various scales (7B, 13B, 70B) under permissive licenses to capture adoption and upsell fine-tuning services.

5. **Corporate backbone model licensing**: License Foil-architecture models to enterprises for internal fine-tuning, positioning around cost and speed advantages vs. standard transformers.

## Technical Limitations

1. **Limited scope of experiments**: Evaluation is primarily on pretraining loss and standard downstream benchmarks; effects on specialized tasks (coding, reasoning, math) and domain transfer are unclear.

2. **Routing confidence as proxy**: The finding that routing confidence tracks expert health better than load balance is empirical; the paper doesn't provide theoretical justification, so it may not generalize to all architectures or scales.

3. **Attention untying trade-offs**: Untying attention parameters increases per-pass compute slightly and may hurt generalization if not carefully regularized; the paper doesn't deeply analyze when this helps vs. hurts.

4. **Scale uncertainty**: All experiments are in the 20B–100B token range; whether Foil scales to trillions of tokens or very large models (300B+) remains open.

5. **No hardware efficiency benchmarks**: The paper assumes fixed FLOPs/parameters are equivalent across designs; actual wall-clock time and memory overhead of dynamic routing and looping are not measured.

6. **Expert specialization analysis**: Limited investigation into whether experts learn meaningful specialization in flattened vs. unflattened setups, or whether flattening sacrifices interpretability.

## Open Questions

1. How does Foil scale to extremely large models (175B+) and training runs in the trillions of tokens?

2. Does routing confidence remain a reliable health metric when models are fine-tuned or deployed on out-of-distribution data?

3. Can you combine Foil with other MoE improvements (e.g., expert dropout, auxiliary loss variants, or hierarchical routing) and see if benefits stack?

4. What is the actual wall-clock and memory overhead of dynamic routing and looping, especially on GPUs vs. TPUs?

5. How does expert specialization change with flattening — do flattened models learn more or fewer distinct expert roles?

6. Does Foil transfer well to non-LLM domains (vision, graphs, multimodal) or is the benefit specific to sequence modeling?

## Key Takeaway
Flattening mixture-of-experts and untying attention across loop passes improves model quality without extra compute, outperforming unflattened looped baselines.
