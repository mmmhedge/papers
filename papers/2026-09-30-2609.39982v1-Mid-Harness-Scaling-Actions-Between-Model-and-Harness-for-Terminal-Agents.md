# Mid-Harness: Scaling Actions Between Model and Harness for Terminal Agents

**Authors:** Minki Kang, Ryo Hachiuma, Shaokun Zhang, Subhashree Radhakrishnan, Yonggan Fu et al.
**Published:** 2026-09-30 | **arXiv:** [2609.39982v1](http://arxiv.org/abs/2609.39982v1)

## Summary
This paper addresses a critical problem in terminal agents (AI systems that interact with computer environments via commands): even when a language model can generate good actions, execution failures often derail progress. The authors propose Mid-Harness, a technique that samples multiple candidate actions and verifies them before execution, without changing the underlying model or environment interface. They show this approach significantly improves task success rates — for example, raising performance from 50% to 68% on a benchmark — and that stronger verifiers can extract better alternatives from the same generator.

## Theoretical Background
Terminal agents operate in a reinforcement learning framework where models generate natural language commands (e.g., shell commands) that execute in a real or simulated environment. The core challenge is that language models are trained primarily for text prediction, not for generating syntactically correct, semantically safe commands that won't corrupt state. Prior work has focused on improving the generator itself (via better pretraining, instruction tuning, or trajectory-level training). This paper builds on the insight that at test time, you can decouple action generation from action verification — a principle familiar in ensemble methods and verifier-based decoding (where a separate model learns to score outputs from a generator).

## Core Contributions
1. **Mid-Harness framework**: A practical mechanism to insert sampling and verification between model and environment without modifying either component. This is valuable because it applies to any model–harness pair post-hoc.
2. **Empirical characterization of verification quality**: The paper shows that weak verifiers (e.g., simple syntax checkers) struggle to exploit multiple samples, but capable verifiers (like GPT-5.6) can reliably select better actions from the same generator.
3. **Cost–benefit analysis of test-time compute**: Demonstrates that action-level scaling (sampling 8 actions with strong verification) is more token-efficient than trajectory-level scaling (rerunning the full task) for improvements in Pass@1.
4. **Distillation pathway**: Shows that knowledge from a strong verifier can be distilled into a weaker model (TMAX-9B), improving performance while keeping the generator fixed.

## Connections to Other Work
This work relates to several research directions:
- **[[Verifier-based decoding]]** and outcome-supervised verifiers in language models, where a separate model learns to score candidate outputs.
- **[[Test-time compute scaling]]**: Similar to recent work showing that sampling and filtering at inference time can improve LLM performance (e.g., [[Best-of-N sampling]], [[Speculative decoding]]).
- **[[Reward modeling]]** in RL and RLHF contexts — the verifier essentially learns a reward signal for actions.
- **[[Multi-step reasoning]]** and planning in agents, where intermediate verification can prevent catastrophic failures.
- Related to the broader problem of **[[Alignment in autonomous agents]]** — ensuring that generated actions are safe and effective.

## Practical Applications
1. **Code generation and command-line agents**: Preventing execution of invalid `pip install` or system commands that corrupt environments or waste compute.
2. **Robotic manipulation systems**: Verifying planned actions (e.g., "pick object A") before execution, reducing physical trial-and-error and equipment damage.
3. **Database query agents**: Sampling multiple SQL queries and verifying them before expensive execution on production databases.
4. **Scientific experiment automation**: Sampling experimental procedure steps and validating them (e.g., checking reagent compatibility, hardware constraints) before committing lab resources.
5. **Enterprise automation workflows**: Verifying high-stakes commands (deployments, data deletions) before forwarding to execution systems.

## Product & Startup Ideas
1. **Verification-as-a-Service for AI Agents**: A middleware SaaS that sits between any model API and execution environment (terminal, database, robotic API) and provides pluggable verifiers (ranging from cheap syntax checkers to premium LLM-based verifiers). Customers pay per verification call; verifiers improve over time via distillation.
2. **Safe Terminal Agent IDE**: A developer tool that runs AI-generated shell commands in a sandboxed environment, displays candidate commands with verification scores, and lets engineers approve before live execution. Includes distilled verifiers tuned to the user's codebase and environment.
3. **Autonomous Lab Assistant**: A SaaS for life sciences that generates and verifies experimental protocols (liquid handling, incubation steps, assay procedures) before uploading them to lab automation hardware. Combines domain-specific verifiers with cost tracking.
4. **AI Workflow Validator**: Enterprise software that intercepts LLM-generated database queries, API calls, and infrastructure changes; verifies them against security policies and cost models; and enforces approval gates. Targets DevOps and data engineering teams.
5. **Verifier Distillation Platform**: A tool that lets companies distill expensive verifiers (e.g., GPT-5-scale models) into cheaper, faster local models (e.g., TMAX-9B) tuned to their specific domain, reducing inference costs while maintaining quality.

## Technical Limitations
1. **Verifier cost and latency**: Strong verifiers (like GPT-5.6) are expensive and slow. If verification cost exceeds generation cost, sampling becomes uneconomical. The paper doesn't fully explore the trade-off under realistic pricing.
2. **Verifier generalization**: A verifier trained on one environment or task distribution may fail to detect errors in new environments. The paper tests on TerminalBench-Lite but doesn't stress-test cross-domain transfer.
3. **Silent failures**: Some incorrect actions don't fail visibly (e.g., a command that silently produces wrong output). A verifier that only checks syntax or immediate error codes will miss these.
4. **Distillation bottleneck**: Knowledge distillation from a capable verifier to a smaller model (TMAX-9B) may lose nuance, especially for edge cases or adversarial inputs.
5. **Scalability to long horizons**: The paper focuses on single-action verification. In multi-step tasks, a bad action early on might not trigger immediate errors but corrupt state for future steps, making post-hoc verification harder.
6. **Environment assumptions**: The approach assumes a deterministic or near-deterministic environment. Stochastic environments may make verification unreliable.

## Open Questions
1. **How does verification performance degrade with domain shift?** Test on agents trained on TerminalBench transferring to real-world terminal tasks or different operating systems.
2. **Can we learn verifiers from trajectory-level feedback?** Rather than supervised fine-tuning, can a verifier be trained via RL to maximize downstream task success?
3. **What is the optimal allocation of test-time compute between sampling, verification, and trajectory re-rolling?** The paper compares sampling vs. trajectory scaling but doesn't solve the general allocation problem.
4. **How do verifiers perform on adversarial or out-of-distribution actions?** Can an agent fool a verifier into approving a harmful action?
5. **Can verifiers be made interpretable?** If a verifier rejects an action, can it explain *why* to the user or downstream system?
6. **How much data does a verifier need to distill effectively?** What is the sample complexity of distilling from GPT-5.6 to TMAX-9B on a new task?
7. **Does verification help with other agent architectures** (e.g., those with explicit planning or world models), or is the benefit primarily for sequence-generation-based agents?

## Key Takeaway
Sampling actions with strong verification improves terminal agent success more efficiently than rerunning entire trajectories.
