# Securing Agentic AI: From Per-Action Checks to Trajectory Assurance

**Authors:** Alireza Lotfi, Subangkar Karmaker Shanto, Imtiaz Karim, Elisa Bertino
**Published:** 2026-08-03 | **arXiv:** [2608.01558v1](http://arxiv.org/abs/2608.01558v1)

## Summary
This paper identifies the security and safety challenges that arise when autonomous AI agents—especially those built on large language models—are deployed to execute real-world tasks under operational, regulatory, and organizational constraints. Rather than treating security as a bolt-on safeguard, the authors argue it must be built into agent architectures from the ground up, addressing vulnerabilities across the entire stack: from single-agent prompt injection to multi-agent trust and delegation, down to model provenance and behavioral containment.

## Theoretical Background
The paper builds on emerging work in autonomous agent safety and secure system design. Key prior concepts include:

- **Agentic AI**: systems where LLMs make decisions and take actions over time, often delegating tasks or communicating across organizational boundaries
- **Threat modeling**: the security community's long-standing practice of systematically identifying attack surfaces and adversarial assumptions
- **Invariants and constraints**: the formal systems idea that certain properties must hold across all system states, not just individual steps
- **Supply-chain security**: lessons from software and hardware security about verifying integrity and provenance at every layer

The paper synthesizes these perspectives rather than introducing fundamentally new theory, positioning security as an *architectural property* rather than a post-hoc policy layer.

## Core Contributions
- **Taxonomy of attack surfaces**: systematic mapping of vulnerabilities across single-agent (prompt injection, memory poisoning, tool-interface attacks) and multi-agent (delegation trust, communication integrity, capability mismatch) layers
- **Behavioral containment problem**: explicit formulation that individual action checks are insufficient—sequences of valid actions can collectively violate system-level safety invariants
- **Architectural security principle**: argument that verifiable security properties must be embedded in runtime protocols and execution control planes, not just guidance or filtering
- **End-to-end observability framework**: identification of provenance, accountability, and traceability as critical but largely unsolved problems in agentic systems
- **Roadmap unification**: demonstrates that seemingly disparate challenges (prompt security, multi-agent trust, model routing) share a common root—the need for verifiable behavioral guarantees

## Connections to Other Work
This work sits at the intersection of:
- **[[Alignment]]**: ensuring agent behavior aligns with human intent and system constraints; this paper extends alignment from a single-agent, value-learning problem to a multi-agent, constraint-satisfaction one
- **[[Agents]]** and **[[Multi-agent-systems]]**: complements recent work on autonomous agent coordination but foregrounding adversarial and failure modes
- **Security and formal methods**: relates to classical work on access control, capability systems, and runtime monitoring, but applied to the new context of LLM-based systems
- **RLHF and interpretability work**: while not explicitly discussed, the paper implicitly critiques the assumption that fine-tuning alone ensures safety—behavioral containment requires architectural support

The paper does *not* propose specific defenses or verification algorithms; it frames the problem space.

## Practical Applications
- **Enterprise automation**: deploying LLM agents for finance (expense approval, risk assessment), HR (candidate screening, onboarding), or supply-chain tasks where each action is auditable and constrained
- **Regulated industries**: healthcare (treatment recommendation systems), law (document review, compliance checking), where agents must provably respect regulatory boundaries
- **Multi-tenant cloud platforms**: ensuring one customer's agent cannot escape its isolation boundary or interfere with others' tools and data
- **Inter-organizational workflows**: enabling agents to safely delegate across company boundaries (vendor portals, client APIs) with cryptographic or cryptographic-ready trust anchors
- **Audit and forensics**: building agent systems where every decision, tool invocation, and delegation is logged and verifiable for compliance reviews

## Product & Startup Ideas
1. **Agent Security Runtime**: a middleware layer (akin to a sandbox or sidecar) that intercepts agent actions and enforces trajectory-level constraints—e.g., "no two financial transfers over $X in a single session" or "tool A can only be called after approval from tool B"

2. **Agent Provenance & Audit Platform**: a SaaS offering that provides cryptographic proof of agent behavior, model versions, and delegation chains for regulated enterprises—think "blockchain for agent actions" without actual blockchain overhead

3. **Multi-agent Trust Protocol**: a library/framework for secure delegation between agents across organizational boundaries, using capability-based security and decentralized identity to enable cross-company agent workflows

4. **Behavioral Constraint Compiler**: a tool that translates high-level business rules and regulatory requirements into executable constraints on agent trajectories, formally verifying that policies cannot be circumvented

5. **Agent Red-Team-as-a-Service**: automated adversarial testing platform that systematically probes agent systems for behavioral violations (e.g., sequences of actions that collectively breach invariants even if each action is individually allowed)

## Technical Limitations
- **No concrete defenses proposed**: the paper identifies problems but offers no algorithms, protocols, or reference implementations; applicability to real systems remains undemonstrated
- **Assumption of trusted runtime**: most proposals implicitly assume the execution environment itself is trustworthy; doesn't address threats within or below the OS/hypervisor level
- **Scalability of trajectory verification**: checking all possible sequences of actions is computationally hard; the paper doesn't discuss how to make constraint enforcement efficient for high-frequency agents
- **Definition ambiguity**: terms like "behavioral containment" and "system-level invariants" are introduced informally; lack of formal semantics may hinder implementation
- **Multi-agent trust still open**: the paper acknowledges that identity, delegation, and cross-organizational capability control are "largely open problems"—minimal guidance on how to solve them
- **Model provenance**: assumes verifiable model provenance is possible; doesn't address fine-tuning, LoRA, or other adaptation that obscures model identity

## Open Questions
- How do you formally specify and verify trajectory-level safety invariants without requiring exhaustive enumeration of all possible action sequences?
- What is the minimal trusted computing base (TCB) for agent security, and how much can be pushed into untrusted layers (e.g., the LLM itself)?
- Can decentralized identity and capability-based security (e.g., from OS kernel research) be adapted to agent delegation across organizational boundaries?
- How do you balance observability (logging all agent behavior for audit) with privacy (e.g., PII in prompts, proprietary tool data)?
- What do threat models look like for agents that interact with external, adversarially-controlled APIs or data sources?
- Can you design an agent architecture that is *provably* resistant to prompt injection while retaining the flexibility of LLM-based instruction following?

## Key Takeaway
Securing AI agents requires built-in architectural guarantees about behavior sequences, not just per-action filtering.
