# SWE-Touch: Benchmarking Coding Agents When Users Touch the Code

**Authors:** Yuqiao Tan, Jinxiang Meng, Fangyu Lei, Minzheng Wang, Shizhu He et al.
**Published:** 2026-08-03 | **arXiv:** [2608.02499v1](http://arxiv.org/abs/2608.02499v1)

## Summary
This paper introduces SWE-Touch, a benchmark for testing how well coding agents handle real-world software development where users actively modify code during task execution. The authors stress-test nine coding models by injecting "counter-edits"—plausible but conflicting code changes—into shared workspaces and measure whether agents can adapt. They find that strong models still struggle with this collaborative scenario, dropping 7.7 percentage points in task resolution, revealing gaps in workspace awareness and conflict resolution.

## Theoretical Background
The paper builds on recent work in autonomous software engineering, particularly the [[SWE-bench]] family of benchmarks which evaluate coding models on real GitHub issues. Prior work treats agents as operating in isolation or with limited user interaction (typically messages only). This paper extends that model to reflect actual development workflows where multiple parties edit shared code. The evaluation uses large language models (LLMs) fine-tuned or prompted for code generation and repair tasks—models like Claude, GPT-4, and specialized coding LLMs that process code as sequences of text tokens and generate edits.

## Core Contributions
1. **SWE-Touch framework**: A methodology for injecting validated counter-edits (conflicting user modifications) into task-relevant code regions at points when agents are actively working on those regions.
2. **Counter-edit mining**: A technique to identify task-critical code regions from multiple repair trajectories and generate plausible user edits using a separate patch generator.
3. **Empirical finding on degradation**: Demonstrated that counter-edits cause measurable performance drops (7.7 pp on SWE-bench Verified) across multiple benchmarks and model scales, including longer-horizon tasks.
4. **Root-cause analysis**: Trajectory analysis revealing that failures stem from limited workspace awareness—agents either retain conflicting code or overwrite user changes without sufficient re-inspection or test validation.

## Connections to Other Work
This work extends [[SWE-bench]] and [[SWE-Bench Pro]] benchmarks toward more realistic multi-agent and human-in-the-loop scenarios. It relates to broader questions in [[alignment]] around autonomous agents following human intent when that intent conflicts with their prior planning. The emphasis on state awareness and adaptive behavior connects to challenges in [[agents|agent design]] for open-ended environments. The focus on code understanding and repair is rooted in neural program synthesis and code LLM research but adds a novel interactive dimension.

## Practical Applications
1. **IDE-integrated AI pair programmers**: Tools like GitHub Copilot could use these findings to detect when user edits conflict with pending refactorings and proactively alert or reconcile changes.
2. **Continuous integration for AI-assisted development**: CI pipelines that coordinate agent-generated changes with human modifications by detecting conflicts and triggering targeted validation.
3. **Team-based code review systems**: Platforms that track when agents and humans are working on overlapping code and suggest merge strategies or re-verification steps.
4. **Autonomous bug-fix systems for open-source projects**: Automated bots that submit pull requests but gracefully adapt when maintainers push changes to the same files before the PR is merged.

## Product & Startup Ideas
1. **CodeSync Pro**: A VS Code / JetBrains plugin that runs coding agents in the background while detecting real-time user edits, auto-reconciling conflicts and re-running tests on affected code regions.
2. **AgentOps for Engineering Teams**: A SaaS dashboard monitoring multiple coding agents in a shared monorepo, detecting workspace collisions, and orchestrating safe handoffs between agent and human edits.
3. **Conflict-Aware Code Generation API**: A managed LLM API endpoint that accepts both a task and a "conflict context" (recent code diffs) and returns edits that are compatible with ongoing changes.
4. **AutoPatch Validation**: A service that wraps agent-generated code fixes with automated workspace-change detection and differential test suites, ensuring agent outputs don't break human-contributed code.
5. **Multi-Agent Orchestration Platform**: Infrastructure for coordinating multiple coding agents and humans on the same codebase with built-in change tracking, merge resolution, and state reconciliation.

## Technical Limitations
1. **Counter-edit realism**: The validity of Counter-Edits depends on the User Patch Generator; unrealistic edits may not stress the agents in meaningful ways.
2. **Scope of tasks**: Evaluation is limited to SWE-bench tasks (GitHub issues); behavior in longer-running, more complex projects or domains (systems programming, distributed systems) is untested.
3. **Timing sensitivity**: The injection point of counter-edits is critical; the paper does not fully explore sensitivity to when edits are introduced relative to agent progress.
4. **Testing infrastructure**: Results assume agents can run tests to validate code; real workspaces may have expensive, flaky, or unavailable tests.
5. **Scalability to large codebases**: Experiments are on repositories of moderate size; behavior in multi-million-line industrial codebases is unclear.
6. **Model diversity**: Only nine models tested; findings may not generalize to newer architectures or proprietary models.

## Open Questions
1. How do agents perform if they are *aware* that code has changed (e.g., via explicit notifications or diff summaries)? Does simple notification close the gap or are deeper reasoning changes needed?
2. Can agents be trained or prompted to automatically re-test affected regions after detecting workspace changes? What prompting strategies work best?
3. How does the severity and type of counter-edit (deletion vs. modification vs. addition) affect agent robustness differently?
4. Do agents learn to handle collaborative edits better with in-context examples or fine-tuning on multi-agent scenarios?
5. Can we design agent architectures with explicit "conflict detection" and "reconciliation" modules, and would they outperform end-to-end models?
6. How do results scale to truly large monorepos with complex dependency graphs and many concurrent developers?

## Key Takeaway
Coding agents fail to adapt when users modify shared code during task execution, revealing a critical gap between isolated and collaborative development workflows.
