# VAKRA: Evaluating Multi-Hop Reasoning Across APIs and Retrieval Under Tool-Use Policies

**Authors:** Ankita Rajaram Naik, Anupama Murthi, Benjamin Elder, Siyu Huo, Raavi Gupta et al.
**Published:** 2026-08-12 | **arXiv:** [2608.12282v1](http://arxiv.org/abs/2608.12282v1)

## Summary
This paper introduces VAKRA, a benchmark for evaluating AI agents on their ability to reason across multiple APIs and documents while following tool-use constraints. The benchmark reveals that even state-of-the-art models struggle significantly with compositional reasoning and policy constraints, dropping from 70% accuracy on simple tasks to as low as 2.4% on policy-constrained questions — problems that stem not from technical tool invocation failures but from language-level reasoning challenges like entity disambiguation.

## Theoretical Background
This work builds on the tradition of agent benchmarking (extending ideas from [[ReAct]] and tool-use evaluation frameworks) and the broader challenge of multi-hop reasoning in language models. The paper assumes agents operate via a ReAct harness — a loop where language models reason in natural language, decide which tools to call, and interpret results. It builds on retrieval-augmented generation (RAG) concepts but extends them to handle structured APIs alongside unstructured documents. The core assumption is that real enterprise agents must solve problems that require reasoning chains across multiple information sources and respecting operational constraints expressed in natural language.

## Core Contributions
1. **VAKRA benchmark**: 8,000+ executable APIs across 62 domains with grounding in live API endpoints, enabling real correctness verification rather than simulated success.
2. **Three-tier difficulty progression**: Single-hop endpoint tasks → multi-hop reasoning over composed APIs → policy-constrained reasoning over multiple sources.
3. **Failure analysis**: Systematic trace analysis showing that language-mediated reasoning (entity disambiguation, cross-source grounding) is the bottleneck, not tool invocation mechanics.
4. **Open-weight + frontier model evaluation**: Standardized comparison across models using a fixed ReAct harness to isolate model capabilities from architecture choices.

## Connections to Other Work
This work extends [[ReAct]]-style agent frameworks and relates to [[RLHF]] and [[alignment]] work in constraining agent behavior. It sits in the intersection of multi-hop reasoning (common in QA benchmarks like HotpotQA) and tool-use learning (similar to [[Toolformer]] and [[Function Calling]]). The policy constraint evaluation connects to safety and alignment concerns — agents must not just reason correctly but respect operational guardrails. The finding that language reasoning is the bottleneck contrasts with optimism about [[mechanistic-interpretability]] approaches that assume reasoning is composable.

## Practical Applications
1. **Enterprise knowledge assistants**: Financial compliance agents that must query multiple data sources (ledgers, documents, policy databases) while respecting access controls and regulatory constraints.
2. **Customer support automation**: Multi-hop ticket resolution requiring reasoning across billing APIs, product catalogs, and documentation while following escalation policies.
3. **Internal IT automation**: Agents for infrastructure queries and changes that must reason across multiple APIs (monitoring, configuration, access logs) while enforcing change management policies.
4. **Legal research systems**: Contract analysis requiring reasoning across document repositories, regulatory databases, and case law while respecting attorney work product constraints.

## Product & Startup Ideas
1. **Enterprise Agent-as-a-Service platform**: A wrapper service that takes unstructured business questions, automatically decompose them into API calls across customer backends (Salesforce, Workday, ERPs), enforces policy constraints, and returns verified results. Charge per-query.
2. **Policy-Constrained API Orchestration Engine**: Middleware that sits between LLMs and enterprise API ecosystems, enforcing role-based reasoning constraints and automatically blocking unsafe multi-step chains before execution.
3. **Agent Diagnostic & Tuning SaaS**: Tools for enterprises to test their LLM agents against VAKRA-style benchmarks, identify reasoning bottlenecks (entity grounding, cross-source alignment), and recommend fine-tuning strategies.
4. **Composable RAG for APIs**: A platform that automatically generates safe, multi-hop reasoning chains by learning from VAKRA-style examples, helping teams deploy agents without extensive prompt engineering.
5. **Compliance Audit Agent**: An internal tool for enterprises to verify their deployed agents stay within policy constraints by replaying traces against VAKRA-style test cases with policy violation detection.

## Technical Limitations
1. **Fixed ReAct harness**: The evaluation isolates model capability but may not reflect how agents perform in other architectures (e.g., tree-search, hierarchical planning, learned routing) — the findings may not generalize to non-ReAct paradigms.
2. **API realism**: While APIs are live, the selection of 62 domains may not represent the long tail of enterprise integrations; results on internal or niche APIs could differ.
3. **Policy representation**: Policies are expressed in natural language — the benchmark doesn't test agents' robustness to adversarial or ambiguous policy statements, which are common in real compliance settings.
4. **Grounding evaluation**: The paper diagnoses entity disambiguation as a failure mode but doesn't provide a systematic methodology for measuring or improving grounding performance.
5. **Compositionality ceiling**: Tasks are limited to a certain reasoning depth; it's unclear how much performance degrades on deeper chains or on problems requiring dynamic re-planning.

## Open Questions
1. **Why does entity grounding fail?** Is it insufficient context in the prompt, lack of fine-tuning on cross-source alignment, or fundamental limits of next-token prediction? What in-context learning strategies help?
2. **Can policy constraints be learned?** Is it better to enforce policies as hard constraints in the agent loop, or can models learn to internalize them through few-shot examples or fine-tuning?
3. **How much does architecture matter?** Do agents with explicit planning or retrieval-augmented reasoning (beyond ReAct) close the gap on policy-constrained reasoning?
4. **Scalability of correctness verification**: How do you verify correctness when APIs fail, return stale data, or have side effects? Can VAKRA handle eventual consistency or distributed systems?
5. **Human-in-the-loop strategies**: For the hardest tasks (2.4% accuracy on unanswerable queries), what interaction patterns between humans and agents maximize task success while minimizing human effort?

## Key Takeaway
State-of-the-art LLM agents fail dramatically on multi-hop reasoning over APIs and policy constraints, not because they can't call tools, but because they struggle to ground entities and reason across sources.
