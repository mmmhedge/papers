# Rethinking Inference-Time Scaling in Local Computer-Use Agents: Failure Modes and Compute Tradeoffs

**Authors:** Woongkyu Lee, Jungwook Choi
**Published:** 2026-07-30 | **arXiv:** [2607.28573v1](http://arxiv.org/abs/2607.28573v1)

## Summary
This paper investigates how to make computer-use agents (AI systems that interact with computers like humans do) work better when running on consumer hardware with limited computing power. The authors test different strategies for using extra computation during task execution and find that while some approaches help, they often hit diminishing returns and shift problems rather than solve them—suggesting that local agents need smarter resource allocation and failure-aware designs.

## Theoretical Background
Computer-use agents are systems that take screenshots, understand visual interfaces, and execute actions (clicking, typing) to accomplish tasks autonomously. Inference-time scaling refers to the practice of using extra computation during a task's execution—not during training—to improve performance. Recent work on frontier large language models (LLMs) has shown that allocating more compute at inference time can boost reasoning and task success. However, most of this research focuses on models running on powerful servers. The paper builds on established agent evaluation benchmarks (OSWorld) and multimodal vision-language models that combine text and image understanding.

## Core Contributions
- **Systematic empirical taxonomy** of inference-time scaling in local agents across four dimensions: contextual (additional history/context), temporal (longer reasoning horizons), structural (decomposing tasks into substeps), and parallel (running multiple reasoning paths).
- **Failure mode analysis**: Shows that additional compute often shifts failure types rather than eliminates them. For example, contextual scaling reduces repetitive failures but increases premature false successes (the agent thinks it succeeded when it hasn't).
- **Quantified tradeoffs** demonstrating that temporal scaling (longer horizons) often extends erroneous trajectories rather than correcting them, and structural decomposition introduces planning overhead that can harm performance in 7B-parameter models.
- **Practical finding** that parallel scaling only partially mitigates failures and requires substantial computational overhead, making it impractical for truly local deployment.

## Practical Applications
- **Local privacy-preserving document automation**: Running agents on-device to process sensitive forms, contracts, or medical records without cloud uploads.
- **Edge manufacturing and warehouse systems**: Autonomous agents controlling industrial interfaces or inventory systems on factory floors with unreliable internet.
- **Offline accessibility tools**: Screen-reader or accessibility agents running locally on older hardware for visually impaired users.
- **Personal productivity assistants**: Local agents managing email, calendar, and desktop tasks without relying on cloud infrastructure.
- **Embedded customer service**: Handling user support tickets by autonomously navigating internal systems in companies with strict data residency requirements.

## Product & Startup Ideas
1. **LocalAgent Studio**: A toolkit for building and deploying custom computer-use agents with built-in failure detection and compute-aware routing—routes complex tasks to cloud when needed, simple tasks run locally. Target: mid-market enterprises with privacy requirements.
2. **Agent OS Layer**: A system-level service that profiles hardware, predicts failure modes for different inference-time scaling strategies, and automatically allocates compute (contextual vs. temporal vs. parallel) per task. Monetize through per-task metering.
3. **Failure-Aware Agent Wrapper**: Middleware that wraps existing local agents, detects emerging failure modes (false successes, stalled trajectories), and applies corrective interventions or human escalation. SaaS for regulated industries.
4. **On-Device Agent Hardware Optimizer**: Specialized edge accelerators or chipsets co-designed for computer-use agents, with hardware support for selective context-windowing and failure monitoring. Target: device manufacturers and enterprises building proprietary agents.
5. **Agent Capability Marketplace**: A platform where users upload task specifications and agent developers compete to build the most compute-efficient solution, with standardized failure-mode scorecards. Incentivizes pragmatic local-first design.

## Technical Limitations
- **Limited model diversity**: Study covers only three models (Qwen3-VL variants, UI-TARS, OpenCUA). Generalization to other architectures or vision-language models is unclear.
- **Single benchmark**: OSWorld, while comprehensive, may not capture real-world task distributions or failure modes in production environments.
- **No user studies**: The paper evaluates task completion; human perception of failure modes (e.g., false successes) is not measured.
- **Hardware assumptions**: Results are tied to specific local hardware setups; results may differ significantly across GPUs, CPUs, or edge devices.
- **Lack of cost-benefit formalism**: No clear framework for computing the "cost" of different scaling strategies—computational cost, latency, and failure-mode severity are treated separately.
- **Baseline interventions weak**: The paper diagnoses problems but offers limited algorithmic solutions beyond compute allocation.

## Open Questions
- Can failure modes be predicted *before* scaling decisions are made, rather than observed post-hoc? Could learned routing policies improve efficiency?
- What is the optimal mix of contextual, temporal, and parallel scaling for a given hardware budget and task distribution?
- Do smaller, specialized models (fine-tuned for specific domains like form-filling) avoid these scaling tradeoffs, or do the fundamental dynamics persist?
- Can human-in-the-loop correction mechanisms (e.g., asking for confirmation on ambiguous actions) reduce false successes while keeping compute low?
- How do these findings transfer to multi-step workflows where agents chain multiple sub-tasks together?

## Key Takeaway
Adding compute to local agents often just changes which failures happen, not whether they happen—smarter designs are needed, not just more power.
