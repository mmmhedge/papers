# FALCON: A Model and Dataset Agnostic Framework for Synthetic Data Generation for NL2SQL Pairs

**Authors:** Darian Lee, Shannon Rumsey, Jack St. Clair, Xinyi Tang, Aditya Bansal et al.
**Published:** 2026-10-02 | **arXiv:** [2610.03625v1](http://arxiv.org/abs/2610.03625v1)

## Summary
FALCON is a framework for generating synthetic NL-to-SQL training data (natural language questions paired with database queries) that captures real-world complexity and ambiguity. Instead of producing oversimplified examples, it creates challenging, realistic data using compact open-source models—enabling organizations to build better SQL understanding systems without relying on expensive external APIs or human annotation.

## Theoretical Background
NL-to-SQL is the problem of converting human language questions into SQL database queries—a core task in making relational databases accessible to non-technical users. Traditional approaches to training such systems relied on manually-annotated benchmarks (like Spider or WikiSQL), which are expensive to create and often contain simplified queries that don't reflect real-world database complexity. Recent work has explored synthetic data generation using large language models, but prior methods tend to produce shallow, unambiguous examples that fail to prepare models for genuine difficulty. FALCON builds on prompt-based data generation techniques (common in [[generative-models]] for NL tasks) while adding two key innovations: structured SQL seeding to ensure diverse query complexity, and alignment-based filtering to distinguish genuinely incorrect outputs from legitimately complex but correct ones.

## Core Contributions
1. **Reserved-word SQL seeding + persona-based prompting**: A two-stage generation strategy that explicitly constructs syntactically diverse, complex SQL patterns (joins, subqueries, aggregations) then uses role-based prompts ("you are a database expert") to generate natural language that matches this complexity—rather than sampling language first and hoping the SQL is hard.

2. **Alignment-based filtering**: A novel quality control mechanism that uses semantic similarity to distinguish between queries that are actually wrong versus queries that are correct but structurally complex. This preserves difficulty rather than accidentally filtering out legitimate hard examples.

3. **Empirical validation of complexity transfer**: Demonstrations that models trained on FALCON data outperform baselines *specifically on complex queries*, while mixed training (FALCON + existing benchmarks) recovers performance on simple queries—showing the method generates genuinely harder, more realistic data rather than just different data.

4. **Model- and database-agnostic design**: The framework works with any LLM and any relational schema, enabling local, private data generation without external API dependencies.

## Connections to Other Work
FALCON addresses a known weakness in [[Large Language Models]]-based synthetic data generation: the tendency to produce "easy" examples that don't stress-test downstream models. It relates to broader work on [[Generative Models]] for data augmentation and to curriculum learning (training on progressively harder examples). The filtering strategy echoes contrastive learning approaches that distinguish valid-but-hard negatives from true errors. The SQL seeding component is inspired by template-based generation in semantic parsing, while the persona prompting draws from recent work on prompt engineering and role-based conditioning in LLMs.

## Practical Applications
1. **Enterprise database access layers**: Companies with proprietary database schemas can now generate large, realistic training sets locally without hiring annotators or exposing data to third-party APIs.

2. **Business intelligence tools**: BI platforms (Tableau, Power BI, etc.) can fine-tune internal models to handle complex queries on real customer schemas, improving natural language querying accuracy.

3. **Domain-specific SQL assistants**: Healthcare, finance, or logistics firms can create custom data generation pipelines tuned to their schema complexity and typical user query patterns.

4. **Data annotation workflows**: Use FALCON-generated data as seed examples to guide human annotators toward realistic complexity levels, reducing annotation time while improving quality.

## Product & Startup Ideas
1. **SaaS synthetic data generator for databases**: A hosted service where users upload their database schema and receive a dataset of NL-to-SQL pairs automatically tuned to their schema's complexity—sold as a data generation service for ML teams training semantic parsing models.

2. **Embedded fine-tuning service for BI platforms**: Integrate FALCON into Tableau/Power BI/Looker to automatically improve their natural language query engines by generating training data from customer schemas without manual labeling.

3. **Privacy-first database querying**: A local-first tool that generates synthetic training data on-premise, then trains a proprietary model for natural language access to sensitive databases (healthcare, finance) without cloud dependency.

4. **Query complexity benchmarking SaaS**: Offer organizations a way to measure and improve their database schema's "queryability"—generate difficulty-stratified benchmarks and identify schema design patterns that make natural language access harder.

5. **SQL skill training platform**: A B2B2C product for enterprise training departments: auto-generate realistic NL-to-SQL exercises tailored to employees' actual database schemas, with difficulty progression built in.

## Technical Limitations
1. **Schema expressiveness assumptions**: The method assumes relatively clean, well-documented schemas. Highly denormalized or legacy schemas with unclear relationships may produce poorly grounded examples.

2. **Semantic validity isn't guaranteed**: Alignment-based filtering helps but isn't foolproof—some generated SQL may be syntactically valid but semantically nonsensical (e.g., selecting irrelevant columns). The paper doesn't address this deeply.

3. **Language-SQL mismatch at scale**: As database schemas grow larger and more complex, the model's ability to consistently ground language to the correct schema entities degrades (a known limitation of LLM semantic parsing).

4. **Limited to SQL**: The framework is specific to SQL; it doesn't generalize to other structured query languages (SPARQL, Cypher) or non-relational databases (NoSQL, graph databases).

5. **Human evaluation scale**: Quality validation was done on a subset of examples—it's unclear how the method scales to very large synthetic datasets or how often drift occurs in model-generated data as generation runs longer.

## Open Questions
1. **How does FALCON perform on truly out-of-distribution schemas** (very large, unfamiliar industry domains)? Does the method degrade gracefully or fail sharply?

2. **Can difficulty be predicted *before* generation**, rather than discovered post-hoc through filtering? This would enable more efficient data generation.

3. **What's the interplay between model size and data quality?** The paper uses compact models—does larger model generation produce better data, and at what cost-benefit tradeoff?

4. **How does mixed training behave with varying ratios of FALCON vs. benchmark data?** The paper tests one ratio; a more detailed curriculum analysis would be valuable.

5. **Can FALCON be extended to multi-hop, cross-database queries** or federated databases? Real enterprises often have complex, linked schemas.

## Key Takeaway
Generate realistic, hard NL-to-SQL training data locally using small models and smart filtering—no expensive APIs, no human annotation at scale.
