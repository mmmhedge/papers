# VISA: A Structured Description Protocol for Agent-Based Simulation Models Towards Machine Reproducibility

**Authors:** Zhou He
**Published:** 2026-07-30 | **arXiv:** [2607.28027v1](http://arxiv.org/abs/2607.28027v1)

## Summary
This paper introduces VISA, a standardized protocol for describing agent-based models (ABMs) in a machine-readable format using eight interconnected tables. Agent-based models are simulations where many independent agents interact—they're widely used in social science, economics, and engineering, but currently impossible to reproduce because their rules are scattered across prose, code, and unwritten assumptions. VISA solves this by making model specifications unambiguous and checkable, enabling LLMs and code generators to automatically reproduce models across different platforms.

## Theoretical Background
Agent-based models have been used for decades to simulate complex systems (crowds, markets, epidemics) where global behavior emerges from local agent interactions. The reproducibility crisis in ABMs parallels broader reproducibility challenges in computational science: models published in papers cannot be reliably reconstructed by other researchers. Prior work in computational reproducibility has focused on code documentation and data sharing, but ABMs are uniquely difficult because their behavior logic is often implicit or embedded in platform-specific frameworks (NetLogo, AnyLogic, MESA). VISA builds on principles from formal specification languages and structured knowledge representation, applying them to the ABM domain.

## Core Contributions
1. **The VISA protocol itself**: A minimal, complete specification using eight tables (Agent, Variable, Sensing, Internal Function at agent level; Associated Data, Input/Output, Schedule, Validation at model level) that unambiguously describes any ABM.
2. **Nineteen executable consistency rules** that automatically validate whether a model specification is internally coherent, turning "is this model described correctly?" into a checkable property.
3. **Three LLM-executable skills** (authoring, checking, code generation) that operationalize the full loop: author a model in VISA → check it for consistency → automatically generate executable code → reproduce it.
4. **Empirical validation** on three externally authored ABMs, including cross-platform reproduction (NetLogo to Python) and honest demarcation of blockers (proprietary libraries, missing data).

## Connections to Other Work
VISA relates to broader efforts in [[mechanistic-interpretability]] of complex systems by making model behavior transparent and auditable. It shares philosophy with formal specification languages and domain-specific languages (DSLs) in software engineering. The use of LLMs for code generation connects to recent work on [[large-language-models]] for scientific automation. The validation rules resemble constraint-checking in formal methods. The paper implicitly addresses reproducibility concerns raised by the open science movement, similar to work on containerization and executable papers.

## Practical Applications
1. **Academic publishing**: Journals could require VISA specifications alongside ABM papers, making claims checkable by readers and reviewers.
2. **Policy modeling**: Government agencies and central banks use ABMs for economic forecasting and regulation testing; VISA would enable independent audits and comparison across models.
3. **Educational tools**: Students learning agent-based modeling could use VISA as a structured template, reducing ambiguity in assignments and exercises.
4. **Interdisciplinary collaboration**: Teams mixing social scientists (who design models) and engineers (who implement them) could use VISA as a shared contract language.
5. **Model libraries**: Repositories of VISA-specified models could enable automated search, comparison, and reuse across domains.

## Product & Startup Ideas
1. **VISA Compliance Checker SaaS**: A web platform where researchers upload ABM documentation/code, and it automatically generates VISA tables, checks consistency rules, and flags gaps—integrated with journals' submission pipelines.
2. **ABM-to-Code Generator**: A tool that takes a VISA specification, queries an LLM to fill in implementation details, and generates executable code in the user's preferred language (Python, R, Java), with version control for reproducibility.
3. **Model Audit & Certification Service**: Consultancy offering VISA-based audits of proprietary ABMs (finance, policy) to certify reproducibility and identify hidden dependencies—addressing regulatory demands for model transparency.
4. **Interactive VISA Editor**: A graphical interface (like Figma for ABMs) where modelers visually design agents, interactions, and schedules, auto-generating VISA tables and executable code in real time.
5. **Research Data Commons for ABMs**: A curated repository of VISA-specified models with automated testing, versioning, and dependency tracking—enabling researchers to fork and adapt published models like GitHub repos.

## Technical Limitations
1. **Proprietary barriers**: The paper acknowledges that third-party libraries (e.g., AnyLogic's movement engine) cannot be captured in VISA tables if they're closed-source or undocumented—reproducibility hits a wall.
2. **Implicit assumptions**: VISA captures *declared* logic, but not implicit assumptions (e.g., "agents are heterogeneous in ways we didn't document"). Completeness is only as good as the author's transparency.
3. **Scalability for large models**: It's unclear how VISA tables scale for ABMs with thousands of agent types or millions of state variables; the paper tests only three models, all modest in complexity.
4. **LLM dependency**: The three LLM skills assume access to capable models and may fail for edge cases or domain-specific jargon not seen during LLM training.
5. **Platform semantics**: Subtle differences in how platforms handle floating-point arithmetic, random seeds, or scheduling can break reproducibility even if VISA specs match—the protocol doesn't fully solve this.

## Open Questions
1. **Scalability & expressiveness**: Can VISA handle ABMs with learned components (e.g., agents using neural networks)? How would you specify a black-box behavioral model in the eight tables?
2. **Validation scope**: The paper tests three models; what is the protocol's failure rate on a corpus of 100+ published ABMs? Which model types does it struggle with?
3. **Stochasticity & randomness**: How does VISA handle probabilistic agents or models with inherent variance? Can two researchers reproducibly get identical results, or only statistically equivalent results?
4. **Integration with version control**: How would VISA interact with git workflows? Can you diff two VISA specs to see what changed in a model across versions?
5. **Extensibility**: Can domain-specific extensions of VISA (e.g., for ecology, finance, epidemiology) be built without breaking the core protocol?
6. **Human factors**: How much does model author expertise affect VISA adoption? Is there a risk that poorly written VISA specs are even more confusing than prose documentation?

## Key Takeaway
Structured tables and automated validation rules can make agent-based models reproducible and machine-parseable, shifting reproduction problems from invisible code to visible, localized dependencies.
