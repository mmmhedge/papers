# MintEval: Do LLMs Implement the Trading Strategy You Asked For? A Behavioural-Equivalence Benchmark for Natural-Language-to-Strategy Code

**Authors:** Siyu Wang, Yifan Wang, Yuecheng He
**Published:** 2026-10-02 | **arXiv:** [2610.03080v1](http://arxiv.org/abs/2610.03080v1)

## Summary
This paper reveals a critical failure mode in LLMs for trading: generated code executes correctly and produces backtests, but implements a different strategy than what was requested. MintEval is a behavioral benchmark that compares what a model's code *does* (not what it looks like) against reference implementations, showing that even frontier models silently diverge from intended logic on 27.5% of tasks. This matters because silent failures in trading code are worse than obvious errors — they destroy trust and risk capital.

## Theoretical Background
Trading strategy implementation sits at the intersection of natural language understanding and code generation. Prior work in code benchmarks (like HumanEval, MBPP) measure functional correctness via unit tests; finance benchmarks measure forecasting accuracy. But neither captures the core risk: a program can pass unit tests and still execute different risk logic than intended.

The paper draws on the concept of *behavioral equivalence* from software verification — two programs are behaviorally equivalent if they produce identical outputs on identical inputs. MintEval applies this to trading: instead of comparing code structure or final P&L (which conflates strategy design with market alpha), it compares *actions taken bar by bar* on identical market data.

The authors generate reference strategies programmatically from composable building blocks (e.g., moving average crosses, position sizing rules), back-translate them into natural language trader instructions, and measure whether an LLM can re-implement them identically. This isolates implementation fidelity from strategy merit.

## Core Contributions
1. **MintEval Benchmark**: 800 trading strategy tasks with programmatic reference implementations, stratified by execution-measured complexity (τ) independent of description length. This sidesteps the confound that longer descriptions are inherently harder.

2. **Action-level comparison**: Compares execution traces (which bars triggered trades, order sizes, etc.) rather than code similarity or profit. Crucially, this removes alpha — the difference between a strategy's *intended* risk logic and market opportunity.

3. **Silent failure quantification**: Demonstrates that Claude Opus 3.5 (frontier model) accepts 43% of tasks yet fails silently (correct specification, wrong implementation) on 27.5%. Shows that LLM judges of strategy generation accept all silent failures.

4. **Implementation-specification gap**: Even when models correctly *identify* which building blocks compose a strategy (79.2% accuracy on menu selection), 79.2% of correct-specification implementations diverge on >10% of active bars — suggesting the gap is in *code synthesis*, not comprehension.

## Connections to Other Work
This relates to broader concerns in [[Alignment|alignment]] — LLMs producing outputs that appear correct but violate the user's intent. The paper critiques recent strategy-generation benchmarks (e.g., FinRL-based evaluators) for using LLM judges that fail to catch silent errors, similar to how early [[RLHF]] evaluations could be gamed by models that produce superficially appealing but flawed outputs.

Methodologically, it echoes work in [[mechanistic-interpretability]] that measures *what a model actually does* rather than relying on proxy metrics. The action-matching comparison is analogous to comparing execution traces in program synthesis.

## Practical Applications
1. **Trading desk automation**: Finance firms deploying LLMs to translate trader intent into executable strategies need MintEval-style validation before live deployment. A 27.5% silent failure rate is unacceptable for capital allocation.

2. **Quantitative research notebooks**: Traders using LLMs to scaffold strategy code need real-time behavioral validation — the tool should flag divergence between intended and executed logic during backtesting.

3. **Compliance and audit**: Regulators and risk managers need provable behavioral equivalence for strategies deployed via LLMs, not just code review.

4. **LLM fine-tuning for finance**: Using MintEval as a training signal or evaluation harness to specialize models (e.g., via RL or SFT) on trading code generation.

## Product & Startup Ideas
1. **MintEval-as-a-Service**: Hosted behavioral validation for trading code. Upload a strategy description and generated code; get a detailed report of divergence from intent, with explainable diffs of which bars/conditions failed.

2. **Trading Code Copilot**: IDE plugin for quantitative platforms (Python notebooks, strategy backtesting tools) that validates LLM-generated trading code against behavioral specs before execution, with real-time warnings.

3. **Strategy Audit SaaS**: Enterprise tool for hedge funds and prop shops to audit all LLM-generated strategies via action-level comparison, integrated with compliance workflows. Store benchmark results for regulatory discovery.

4. **FinLLM Fine-tuning Service**: Train custom LLMs on trading code using MintEval as the loss signal — optimize for behavioral equivalence rather than surface-level code quality. White-label for trading firms.

5. **Behavioral Code Diffing**: Specialized diff tool for trading code that highlights divergences in *execution behavior* (not just syntax), helping traders understand what changed when they iterate on LLM outputs.

## Technical Limitations
1. **Scope to crypto spot markets**: MintEval v0 is stratified on BTCUSDT 15-min data. Generalization to equities, derivatives (options, futures), multi-asset portfolios, or different time horizons is untested.

2. **Composable building blocks only**: Strategies must assemble from a finite library. This doesn't catch failures in novel, custom logic that doesn't fit pre-defined blocks.

3. **Backtesting as ground truth**: Assumes the market data, frictions model, and order execution assumptions in backtests are accurate. Real market slippage, liquidity, and latency can mask or amplify silent failures.

4. **Action-level granularity**: Comparing bar-by-bar actions works for discrete decision points but may miss subtle logic bugs that only manifest under stress (e.g., rare market regimes, edge cases in position sizing).

5. **No interactive feedback loop**: The benchmark is static. In practice, traders refine strategies iteratively; a single round of LLM code generation is unrealistic.

## Open Questions
1. **Scaling to complex strategies**: How does behavioral equivalence degrade as strategies grow beyond ~5–10 building blocks? Is there a complexity cliff?

2. **Cross-model generalization**: Do models trained on high MintEval scores (via fine-tuning) transfer to unseen strategy types or market regimes?

3. **Root cause analysis**: Can we automatically diagnose *why* an implementation diverged — is it a logic error, off-by-one bug, state management issue, or numerical precision?

4. **Human-in-the-loop refinement**: How many iterations of LLM + human feedback are needed to reach ~95% behavioral equivalence? Is it faster than writing code from scratch?

5. **Adversarial strategies**: Can traders craft strategy descriptions that are intentionally ambiguous, forcing LLMs into silent failures? What linguistic properties make descriptions robust?

6. **Benchmark contamination**: Is MintEval at risk of being memorized by frontier models trained on arXiv preprints? How should the benchmark evolve?

## Key Takeaway
LLMs write trading code that silently executes different strategies than requested — even frontier models fail on 27.5% of tasks — and existing benchmarks don't catch this.
