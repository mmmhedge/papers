# A New Approach to Characterising Optimisation Problems Using Programmatic Representation and Complexity Measures

**Authors:** Marcus Gallagher, Katherine M. Malan
**Published:** 2026-08-09 | **arXiv:** [2608.08898v1](http://arxiv.org/abs/2608.08898v1)

## Summary
This paper proposes a new way to characterize optimization problems by analyzing the complexity of their code implementations, rather than sampling their search landscapes. The authors use Halstead volume (a software complexity metric) as a proxy for problem difficulty and show it correlates with algorithm performance on benchmark problems—offering a fast, transformation-invariant tool for algorithm selection.

## Theoretical Background
The paper builds on two distinct traditions. First, it draws from **algorithm selection** and **meta-learning** — the field of automatically choosing which algorithm works best for a given problem instance. Prior work in this space typically uses empirical features extracted by sampling the optimization landscape (e.g., fitness statistics, ruggedness measures). Second, it borrows from **software complexity theory**, specifically Halstead metrics — an approach from the 1970s that quantifies code complexity through counts of operators, operands, and related statistics. The intuition connecting them is novel: if a function's code is complex to write, perhaps the optimization landscape itself is inherently complex.

## Core Contributions
1. **Programmatic representation as problem characterization**: The core insight is treating the objective function's source code as a direct signal of problem difficulty, rather than requiring landscape sampling.
2. **Halstead volume and entropy adaptation**: Demonstrates that Halstead volume and information-theoretic entropy calculated from code can serve as predictive meta-features without touching the search space.
3. **Empirical validation on BBOB and neural network training**: Shows negative correlation between these code-based measures and algorithm performance, suggesting predictive power for both.
4. **Three key advantages**: No sampling required, invariant to variable/coordinate transformations, and computable in milliseconds.

## Connections to Other Work
This relates to broader meta-learning efforts like [[AutoML]] and algorithm portfolio selection (e.g., per-instance algorithm selection frameworks). It contrasts with landscape-analysis approaches (which sample extensively) and instance-hardness predictors. The use of code as a feature vector is unconventional and sits at the intersection of program synthesis and meta-learning. It could complement or replace [[meta-features]] derived from fitness landscapes, particularly when sampling is expensive.

## Practical Applications
1. **Automated algorithm selection in competitive optimization**: Real-time selection of genetic algorithms, particle swarm optimization, or gradient-based methods for a new problem, given only its code.
2. **Neural architecture search (NAS) meta-learners**: Predicting which search strategy will work best for a given architecture search space without expensive sampling.
3. **Hyperparameter optimization configuration**: Choosing solver settings and strategies for expensive black-box optimization (e.g., in engineering design or Bayesian optimization).
4. **Constraint programming solver selection**: Determining which SAT/SMT solver variant suits an encoded problem.

## Product & Startup Ideas
1. **OptiMeta**: A cloud service that accepts a problem's objective function code and recommends the best solver (genetic algorithm, simulated annealing, gradient descent variant) with predicted runtime/quality tradeoffs.
2. **AutoOptimizer IDE plugin**: Real-time linting and solver-recommendation tool for R/Python/C++ that flags slow-to-optimize code patterns and suggests algorithm configurations.
3. **Algorithm portfolio trading**: SaaS for quantitative funds to automatically route optimization tasks (portfolio rebalancing, parameter tuning) to the fastest solver based on problem code fingerprints.
4. **NAS advisor**: A meta-learning platform that profiles neural network architecture spaces (via their code representation) and recommends search strategies (random, Bayesian, evolutionary) before expensive search.
5. **Problem-difficulty marketplace**: A platform where researchers upload optimization problem instances and receive instant difficulty scores and recommended algorithms, enabling benchmarking and algorithm trading.

## Technical Limitations
1. **Code-to-landscape mapping is speculative**: Halstead volume measures syntactic complexity, not semantic problem hardness. A simple-looking function can hide exponential landscapes (e.g., cryptographic hash); conversely, complex code might implement a smooth problem.
2. **Language and implementation bias**: The same function written in Python vs. C++ has different Halstead metrics. Refactoring or obfuscation changes the score without changing the problem.
3. **No landscape-specific information**: The approach loses information about modality, deceptiveness, or ruggedness—features that strongly influence algorithm performance but are invisible to code analysis alone.
4. **Limited empirical validation**: Tested only on BBOB (artificial, relatively smooth) and neural network training. Generalization to combinatorial, constraint-heavy, or highly multimodal problems is unclear.
5. **Missing operator/operand semantics**: Halstead counts are syntactic; a division operator and a convolution operator are equal, despite very different computational complexity.

## Open Questions
1. **Does the correlation hold across different problem domains** (e.g., combinatorial optimization, constraint satisfaction, multi-objective)?
2. **How does code refactoring and style affect predictive power?** Can we define a "canonical" representation?
3. **Can this be combined with lightweight landscape sampling** (e.g., a few random evaluations) to improve predictions beyond code alone?
4. **Does this extend to dynamically generated or implicit objective functions** (e.g., physics simulations, large language model training)?
5. **What is the theoretical relationship between Kolmogorov complexity and optimization hardness**, and can Halstead metrics serve as a practical approximation?

## Key Takeaway
Code complexity predicts optimization problem difficulty faster and cheaper than landscape sampling, enabling rapid algorithm selection without exploring the search space.
