# HakiCC: LLM-Driven Multi-Agent Design and Optimization of Concurrency Control Protocols

**Authors:** Farzad Habibi, Juncheng Fang, Faisal Nawab
**Published:** 2026-10-01 | **arXiv:** [2610.00889v1](http://arxiv.org/abs/2610.00889v1)

## Summary
This paper presents HakiCC, a system that uses large language models (LLMs) and multiple AI agents working together to automatically design database concurrency control protocols tailored to specific applications. Instead of forcing all applications to use generic protocols like 2PL or OCC, HakiCC generates custom protocols optimized for particular workloads, then further improves them through an evolutionary optimization loop—achieving 50–92% throughput gains on real benchmarks.

## Theoretical Background
Concurrency control protocols are rules that databases use to ensure multiple transactions can run simultaneously without corrupting data or violating consistency. The field has decades of research producing protocols with different trade-offs: 2PL (Two-Phase Locking) prioritizes safety but can be slow; OCC (Optimistic Concurrency Control) assumes conflicts are rare and aborts conflicting transactions retroactively. Conflict-serializability is a formal correctness property—a schedule of transactions is conflict-serializable if it produces the same final state as some serial (non-concurrent) execution. This paper combines LLMs (neural networks trained on vast text that can generate and reason about code) with multi-agent systems (where independent AI agents collaborate to solve problems) to automate the expert-level task of designing and verifying such protocols.

## Core Contributions
1. A two-stage automated pipeline: Stage 1 uses multiple LLM-driven agents to generate a candidate protocol from workload descriptions, then iteratively repairs and formally verifies it for conflict-serializability. Stage 2 applies an LLM-driven evolutionary algorithm (mutations guided by performance feedback) to optimize throughput and correctness for the specific application.
2. Demonstration that automatically generated protocols are not just correct but beat generic baselines significantly (50–92% throughput improvement on TPC-C and AuctionMark workloads).
3. A practical pathway for application designers without CC expertise to obtain high-performance, application-specific protocols.

## Connections to Other Work
This work sits at the intersection of [[Large Language Models]], [[Multi-Agent Systems]], and database systems optimization. It parallels recent efforts using LLMs for [[Program Synthesis]] and automated system design (e.g., using LLMs to generate and repair database query plans). The evolutionary optimization loop echoes classical genetic algorithms and modern neuroevolution approaches. Unlike prior work that applies LLMs to individual tasks (e.g., code generation), HakiCC chains agents for collaborative design and verification, addressing the full lifecycle of protocol creation. It also relates to broader trends in applying LLMs to systems research to reduce human engineering effort.

## Practical Applications
1. **E-commerce platforms**: Tailor concurrency protocols to auction or inventory-heavy workloads (like AuctionMark), reducing transaction abort rates and latency during flash sales.
2. **Financial transaction systems**: Generate protocols optimized for high-frequency trading or settlement workloads with distinct conflict patterns.
3. **Multi-tenant SaaS databases**: Design tenant-specific or workload-specific protocols to improve performance for different customer use cases without code recompilation.
4. **Embedded or IoT databases**: Generate lightweight, optimized protocols for resource-constrained environments with predictable access patterns.
5. **Legacy system modernization**: Automatically design drop-in protocol replacements for outdated databases to unlock performance without manual redesign.

## Product & Startup Ideas
1. **HakiCC as a cloud service**: A managed SaaS platform where users upload workload traces or descriptions, receive optimized concurrency control implementations, and benchmark gains—monetize via per-protocol generation or throughput-based pricing.
2. **Database-as-a-Service with adaptive protocols**: A PostgreSQL/MySQL wrapper that learns workload characteristics at runtime and uses HakiCC to automatically swap in optimized protocols, marketed to performance-sensitive SaaS companies.
3. **Performance consulting tool for enterprise DBAs**: A tool DBAs use to audit existing applications, generate custom protocols, A/B test them in staging, and roll out performance wins—charge per enterprise license.
4. **Embedded database customizer**: Pre-generate and package protocol libraries for common domains (e-commerce, banking, IoT), allowing developers to drop them in via a lightweight SDK.
5. **Protocol marketplace**: Let the system generate a portfolio of protocols for a workload, then charge enterprises for selecting and deploying the top-N variants suited to their SLAs or cost constraints.

## Technical Limitations
1. **Verification scope**: The paper verifies conflict-serializability, but doesn't guarantee all non-functional properties (e.g., deadlock freedom, distributed consensus under partitions, or performance under adversarial workloads).
2. **Workload representation**: Success depends on accurate workload descriptions; if the training workload differs sharply from production, the protocol may not generalize well.
3. **Scalability of verification**: As protocol complexity grows, formal verification may become intractable; the paper doesn't discuss complexity bounds or scaling limits.
4. **LLM consistency**: LLMs can produce plausible but subtly incorrect code; repair loops rely on detecting errors post-hoc, not preventing them in generation.
5. **Limited evaluation scope**: Only two benchmarks (TPC-C, AuctionMark) tested; unclear how HakiCC performs on highly irregular or adversarial workloads, or on truly novel transaction patterns.
6. **Distributed systems**: The paper focuses on single-node or simple setups; designing protocols for geo-distributed transactions with network delays is not addressed.

## Open Questions
1. How does HakiCC handle workload drift—does a protocol optimized for one workload degrade gracefully as access patterns change over time?
2. Can the approach extend to other distributed systems problems (consensus, caching, load balancing) beyond concurrency control?
3. What is the minimum workload data required to generate a robust protocol? Can HakiCC synthesize protocols from short traces or synthetic descriptions?
4. How do generated protocols compare to hand-crafted, research-level protocols from recent papers (e.g., Aria, MVCC variants)?
5. Can the framework provide interpretability—e.g., explain to a DBA why a generated protocol is faster for their workload?
6. Does the evolutionary optimization loop ever find fundamentally novel CC strategies, or does it stay within the space of existing protocol families?

## Key Takeaway
LLM-driven agents can automatically design and optimize database concurrency protocols for specific workloads, delivering 50–92% throughput gains over generic baselines.
