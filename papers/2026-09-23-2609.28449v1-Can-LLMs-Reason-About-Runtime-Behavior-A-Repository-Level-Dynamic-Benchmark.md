# Can LLMs Reason About Runtime Behavior? A Repository-Level Dynamic Benchmark

**Authors:** Hamed Taherkhani, Mohammad Abdollahi, Melika Sepidband, Hridya Dhulipala, Tien N. Nguyen et al.
**Published:** 2026-09-23 | **arXiv:** [2609.28449v1](http://arxiv.org/abs/2609.28449v1)

## Summary
This paper introduces SWE-Flux, a benchmark that tests whether large language models can reason about how code actually executes at runtime, not just understand static code structure. The benchmark contains 480 real-world questions drawn from 12 Python repositories, with correct answers automatically extracted from actual program executions rather than written manually or judged by other LLMs. Even the best model only reaches 37% accuracy, revealing that LLMs struggle significantly with dynamic execution reasoning.

## Theoretical Background
The work builds on two related but distinct evaluation traditions. First, repository-level code understanding benchmarks (like SWE-Bench) have emerged to test LLMs on realistic, large-codebase tasks—moving beyond toy snippets. Second, execution-reasoning tasks in program analysis and formal verification have long required systems to simulate or track code behavior. However, these two traditions rarely intersect: most repo-level benchmarks evaluate static code comprehension (can you understand what this code does?) while execution benchmarks tend to stay small (single functions or short traces). SWE-Flux bridges this gap by asking: can LLMs predict concrete runtime behavior—variable values, control flow paths, exception states—across entire repositories? The benchmark leverages automated test execution with instrumentation (collecting actual program traces) to generate ground truth, sidestepping the subjectivity of manual annotation.

## Core Contributions
1. **SWE-Flux benchmark**: A repository-level dynamic execution benchmark with 480 instances across 12 real Python projects, distinguished by oracle-harvested answers from instrumented test execution rather than manual annotation or LLM evaluation.
2. **Comprehensive failure analysis**: Fine-grained breakdown showing LLMs excel at localized invariant reasoning and simple control flow but fail on dataflow tracking, inter-procedural reasoning (following function calls across boundaries), precise state tracking, and aggregating behavior across multiple test cases.
3. **Automated variant generation**: A pipeline that perturbs test inputs to create harder benchmark variants, successfully generating valid variants for ~90% of instances—enabling controlled difficulty scaling without manual effort.
4. **Multi-LLM evaluation**: Systematic assessment of five LLMs, quantifying the gap between static understanding and dynamic execution reasoning.

## Connections to Other Work
This paper directly extends [[SWE-Bench]] and similar repository-level QA benchmarks, but shifts focus from static understanding to runtime behavior prediction. It relates to program synthesis and repair work (e.g., [[Copilot]], neural program verification) which also need execution reasoning, but those typically focus on *generating* code, not *explaining* behavior. The work also connects to mechanistic interpretability research—understanding what models know about computation—though it approaches the question empirically through benchmarking rather than probing model internals. The oracle-harvesting approach echoes automated test-based evaluation in software testing, but applies it to LLM assessment for the first time at scale.

## Practical Applications
1. **Code review assistance**: Helping developers predict edge cases and bugs by asking the model "what will happen if this loop encounters a null pointer?"—SWE-Flux reveals where such predictions fail.
2. **LLM-assisted debugging**: Systems that explain why a test failed by simulating execution; this benchmark identifies when LLM explanations will be unreliable.
3. **Program repair and synthesis**: When generating code fixes, systems must reason about execution impact; SWE-Flux measures readiness for this task.
4. **Test case prioritization**: Ranking which tests are most likely to fail on a code change requires execution reasoning—currently beyond LLM capability at scale.
5. **Security analysis**: Predicting whether a code path leads to a vulnerability (e.g., buffer overflow, SQL injection) requires exact state and dataflow reasoning, exposed as a weak point here.

## Product & Startup Ideas
1. **Execution-aware code assistant**: A VS Code plugin that uses specialized fine-tuned models trained on SWE-Flux data to predict what *actually* happens when you run code, showing likely runtime values inline during editing.
2. **Automated test failure explainer**: A tool that ingests a failing test and uses execution-reasoning-focused LLMs to generate human-readable explanations of *why* it failed (e.g., "variable x is null at line 42 because the loop never entered") rather than just showing stack traces.
3. **Dynamic code review service**: A code review SaaS that flags risky execution patterns (e.g., unbounded loops, uncaught exceptions, state corruption) by reasoning about runtime behavior, marketed to teams burned by static analysis false positives.
4. **Security-focused SAST alternative**: A software composition analysis tool that predicts *exploitable* execution paths in dependencies by reasoning about data flow and control flow, catching vulnerabilities static tools miss.
5. **LLM-powered mutation testing platform**: A service that generates program mutations and uses execution-reasoning models to predict which mutations will be caught by the test suite, helping teams assess test quality.

## Technical Limitations
1. **Limited to Python**: While Python has rich introspection, the benchmark doesn't address polyglot codebases or compiled languages where execution tracing is harder.
2. **Test-grounded only**: Questions are tied to existing test suites; novel execution scenarios not covered by tests cannot be evaluated.
3. **Scalability of oracle generation**: Instrumentation and test execution don't scale infinitely; complex programs with long-running tests may be underrepresented.
4. **Single-execution traces**: The benchmark doesn't capture non-deterministic behavior (race conditions, randomness), which real execution reasoning must handle.
5. **No performance modeling**: Predicting *how fast* code runs (complexity reasoning) is out of scope; only correctness of execution is measured.
6. **Inter-procedural limits**: The paper notes LLMs struggle with cross-function reasoning, but the benchmark may not fully expose how deep that deficit runs in truly complex call stacks.

## Open Questions
1. **Can fine-tuning help?** Does continued pretraining on execution traces or program synthesis tasks significantly improve performance, or is this a fundamental architectural limitation?
2. **What's the role of context length?** Do longer context windows help with inter-procedural reasoning, or is the issue deeper (inability to track state across token distances)?
3. **How do different prompting strategies perform?** Does chain-of-thought prompting, step-by-step execution simulation, or intermediate variable tracking requests substantially close the gap?
4. **Can symbolic execution help?** Should hybrid systems combine LLM reasoning with lightweight static analysis or symbolic execution to improve accuracy?
5. **Generalization beyond test suites**: Can models reason about execution on inputs *not* in the test suite, or is performance purely memorized from training data that resembles the tests?
6. **Why the dataflow failure?** Is it a tokenization problem, attention mechanism limitation, or something else—mechanistic study of where dataflow reasoning breaks would be valuable.

## Key Takeaway
LLMs can understand code structure but mostly fail at predicting what code actually does when it runs, especially across functions and complex state changes.
