# Stealing Reasoning Traces from Proprietary LLM APIs

**Authors:** Alexander Panfilov, David Schmotz, Ilia Shumailov, Luca Beurer-Kellner, Joachim Schaeffer et al.
**Published:** 2026-08-10 | **arXiv:** [2608.09867v1](http://arxiv.org/abs/2608.09867v1)

## Summary
This paper uncovers a critical security vulnerability in how major LLM providers (OpenAI, Anthropic, Google) protect their models' reasoning traces — the step-by-step thinking that models use to arrive at answers. The researchers show that encrypted reasoning blocks are reusable across sessions and users, allowing attackers to "decrypt" them by injecting them into weaker models from the same provider, which then output the reasoning in plaintext. This enables model distillation, large-scale extraction of sensitive personal data, and injection of hidden malicious prompts.

## Theoretical Background
Modern LLMs increasingly use chain-of-thought reasoning — showing their working step-by-step — to improve accuracy, especially on complex tasks. Providers want to protect this reasoning as intellectual property while still enabling users to continue conversations by storing reasoning context. Prior work has shown that encrypted "session tokens" or reasoning blocks are sometimes insufficiently protected. The paper builds on architectural analysis of client-side encryption schemes and prior distillation attacks on machine learning models (where a smaller model learns to mimic a larger one). The key insight is that many systems rely on symmetric or insufficient key management when reasoning traces move between client and server.

## Core Contributions
1. **Architectural vulnerability identification**: Demonstrating that encrypted reasoning blocks are cryptographically identical and interchangeable across users, sessions, and even different models within the same provider's ecosystem — a design flaw enabling reuse.
2. **Practical decryption jailbreak**: A concrete attack that injects encrypted traces into a weaker, less-safeguarded model to force plaintext decoding without ever attacking the target model directly.
3. **Large-scale empirical validation**: Scraped and decrypted 315,320 reasoning blocks from public repositories (GitHub, etc.), recovering 367 PII artifacts and 182 credentials, demonstrating real-world impact.
4. **Four distinct attack vectors**: Anti-distillation bypass, private data extraction, hidden hazard revelation (dangerous reasoning masked by safe outputs), and invisible prompt injection via encrypted payloads in agentic workflows.
5. **Mitigation proposals**: Concrete cryptographic and system-level defenses (per-user keys, reasoning block expiration, integrity checks).

## Connections to Other Work
This paper sits at the intersection of LLM security ([[alignment]]), model extraction / distillation attacks, and cryptographic protocol design. It extends prior work on prompt injection attacks by showing how injection can occur invisibly within encrypted blocks. It relates to broader concerns about [[mechanistic-interpretability]] — the desire to understand model reasoning — but shows a dark side: that reasoning traces themselves are valuable targets. The work also connects to [[agents]] research, where the vulnerability enables poisoning of agentic rollouts (multi-step agent workflows) without visible detection.

## Practical Applications
1. **Incident response for LLM providers**: Detecting and auditing whether reasoning traces have been leaked or decrypted in the wild.
2. **Credential rotation for developers**: Identifying and remediating compromised API keys, passwords, and tokens found in decrypted reasoning blocks scraped from public code repositories.
3. **GDPR/privacy compliance**: Quantifying and managing unintended PII leakage from model reasoning, especially for regulated industries (healthcare, finance).
4. **Secure agentic systems**: Building agent frameworks that validate and isolate encrypted payloads to prevent invisible prompt injection.
5. **Forensic analysis of data breaches**: Recovering sensitive information from cached or logged reasoning blocks that were assumed encrypted.

## Product & Startup Ideas
1. **LLM Security Auditing Service**: A B2B SaaS that automatically scans public repositories (GitHub, Hugging Face, etc.) for leaked encrypted reasoning blocks, decrypts them using this vulnerability, and alerts customers to PII/credentials found — positioning as a "breach detection" tool for LLM users.
2. **Reasoning Block Integrity Monitor**: A proxy service that sits between users and LLM APIs, re-encrypting reasoning blocks per-session with unique keys and checking integrity, preventing reuse attacks.
3. **Agentic Workflow Firewall**: A platform that sandboxes agent reasoning, validates encrypted payloads, and detects invisible prompt injection before execution — marketed to enterprises deploying autonomous agents.
4. **Credential Recovery & Rotation as a Service**: Automatically identify, quarantine, and rotate credentials exposed in decrypted LLM reasoning logs, integrating with secret managers (HashiCorp Vault, AWS Secrets Manager).
5. **Compliance Reporting for LLM Privacy Risk**: Automated reporting tool for regulated companies showing what PII/sensitive data is leaking from encrypted reasoning and recommending mitigations to satisfy GDPR, CCPA, HIPAA audits.

## Technical Limitations
1. **Assumption of weak model availability**: The attack requires the attacker to have query access to a weaker model in the same ecosystem; some providers may isolate their model tiers cryptographically.
2. **Session log publication**: The large-scale PII extraction relied on developers uploading reasoning blocks to public repositories; this is a user behavior problem, not a guaranteed vulnerability.
3. **Per-provider specificity**: Exploits are tailored to each provider's architecture (OpenAI, Anthropic, Google); generalization requires reverse-engineering each system's encryption scheme.
4. **Detection evasion unknown**: The paper doesn't deeply explore rate-limiting or anomaly detection that providers might deploy to catch the decryption jailbreak in real time.
5. **Cryptographic assumptions**: The mitigation strategies assume providers implement proper key management and expiration; legacy systems may resist retrofit.
6. **Scope**: Only addresses client-side reasoning encryption; server-side leaks (e.g., insider threats, unencrypted logs) are out of scope.

## Open Questions
1. **Can providers enforce stronger binding** between reasoning blocks and user/session identity without breaking UX (e.g., long-form reasoning reuse)?
2. **What is the true scale of reasoning-block leakage** across all major providers over time (beyond the snapshot in this paper)?
3. **How do providers detect this attack in real-time?** Are there behavioral signatures (e.g., injecting traces from one model into another)?
4. **Can reasoning be made "disposable"** — computed fresh each time instead of cached — without sacrificing latency and cost?
5. **What is the relationship to formal verification** of cryptographic session protocols for LLM APIs?
6. **How do agentic systems defensibly use reasoning traces?** Is there a way to preserve reasoning reuse without enabling injection?

## Key Takeaway
Encrypted reasoning traces in major LLM APIs are reusable across users and can be decrypted by injecting them into weaker models, enabling distillation, PII theft, and invisible prompt injection.
