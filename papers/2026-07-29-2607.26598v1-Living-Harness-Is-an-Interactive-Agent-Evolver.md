# Living-Harness Is an Interactive-Agent Evolver

**Authors:** Yuetian Du, Yucheng Wang, He Xu, Jiexu Xu, Shanwen Tan et al.
**Published:** 2026-07-29 | **arXiv:** [2607.26598v1](http://arxiv.org/abs/2607.26598v1)

## Summary
This paper introduces Living-Harness, a system that allows LLM-based agents to evolve their operational structure (tools, memory, workflow) after each task rather than remaining static. By extracting lessons from failures and successes into episodic memory and state repair graphs, the agent improves reliability across future tasks. This matters because current LLM agents often repeat the same mistakes even when they've been corrected once—Living-Harness fixes that by treating the agent's guiding structure as continuously learnable.

## Theoretical Background
LLM agents rely on a "harness"—the collection of tools, context, memory buffers, and procedural workflows that guide their interactions with environments. Prior work has established that static harnesses (unchanged after deployment) limit agent reliability; agents can recover from failures mid-episode but don't retain lessons that prevent recurrence. This work builds on the concept of episodic memory in cognitive science and state-based planning in reinforcement learning (using reward signals and structured feedback to refine behavior). The paper also leverages Standard Operating Procedures (SOPs) — structured protocols for decision-making—as a framework for formalizing what should be learned and how.

## Core Contributions
1. **Living-Harness architecture**: A self-evolving harness that treats episodic memory and state transition graphs as learnable, while keeping tools and base context frozen. This design choice prevents catastrophic forgetting while accumulating procedural knowledge.
2. **Evolution-SOP**: A principled procedure that converts completed trajectories and evaluator feedback into two complementary forms of procedural knowledge—episodic patterns (trigger conditions, failure modes, recovery actions) and state repair graphs (nodes, repair edges, rules).
3. **Empirical validation**: 10.07 and 9.91 percentage-point improvements in Pass@1 on τ²-Bench and MultiWOZ-2.4 interactive environments; demonstrated cross-backbone harness portability (the evolved harness works with different LLM backbones).

## Connections to Other Work
This work sits at the intersection of [[RLHF]] (using evaluator signals for improvement), [[in-context learning]] (learning within an episode), and memory-augmented agents. It extends static agent frameworks by adding post-deployment adaptation—related to continual learning and online fine-tuning but specifically focused on procedural knowledge rather than model weights. The episodic memory component echoes work on experience replay and trajectory-based learning. Unlike full model retraining, Living-Harness operates only on the agent's interaction protocol, making it complementary to parameter-efficient adaptation methods.

## Practical Applications
1. **Customer service chatbots**: Agents deployed in contact centers can evolve their troubleshooting flowcharts and recovery strategies based on daily failures, reducing repeat customer escalations.
2. **Autonomous coding assistants**: Can build up state graphs for common debugging patterns (e.g., "when type error on line X occurs, try Y fix first") without retraining the underlying model.
3. **Multi-turn dialogue systems**: Medical or legal AI advisors can refine their conversation flows and knowledge retrieval triggers based on real interactions, improving accuracy over months of deployment.
4. **Robotic task planning**: Robots can update their procedural knowledge graphs (which actions succeed from which states) as they encounter new objects or environmental conditions.

## Product & Startup Ideas
1. **Agent Ops Platform**: A SaaS layer that sits between any LLM API and deployed agents, automatically capturing trajectories and suggesting harness updates via Living-Harness—sold to enterprises running customer-facing AI.
2. **Harness Marketplace**: A marketplace where teams can share and fine-tune evolved harnesses for specific domains (e-commerce, support, coding) without sharing proprietary data.
3. **Continuous Agent Monitoring & Evolution**: A managed service for enterprises that runs Living-Harness updates on a schedule, A/B tests evolved harnesses, and reports which procedural changes had the biggest impact.
4. **Specialized Agent Modules**: Pre-trained, domain-specific harnesses for vertical markets (healthcare intake forms, financial advisory, logistics dispatch) that customers license and then evolve with their own data.
5. **Agent Debugging IDE**: Developer tool that visualizes the state graph and episodic memory of running agents, letting engineers manually edit repairs and test them in simulation before deploying.

## Technical Limitations
1. **Frozen tools and base context**: The method doesn't update the underlying tool set or foundational prompts—only procedural flow. If the base model lacks a critical capability, Living-Harness cannot add it.
2. **Scalability of state graphs**: As the state graph grows (many nodes and repair edges), retrieval and reasoning complexity may increase. No analysis of computational cost with graph size is provided.
3. **Evaluator quality assumption**: Relies on accurate, consistent evaluator signals. Noisy or biased feedback could corrupt the evolved harness.
4. **Limited to procedural failures**: Works well for systematic failure patterns but may struggle with rare or novel failure modes that don't fit the trigger/action abstraction.
5. **Cross-domain generalization unclear**: Evaluated only on two benchmark suites; unclear how harnesses generalize to truly unseen task distributions.
6. **Model backbone assumption**: While harnesses are shown to transfer across backbones, the abstraction may degrade if backbones have very different reasoning styles or output distributions.

## Open Questions
1. How does harness complexity (number of episodic rules, graph size) scale with task diversity? Is there a saturation point beyond which adding more procedural knowledge hurts?
2. Can the method handle adversarial or deliberately misleading feedback from evaluators, or does it need explicit feedback validation?
3. Does Living-Harness transfer from one domain (e.g., customer support) to a related domain (e.g., technical support) without starting from scratch?
4. How would this scale to truly multi-agent scenarios where agents co-evolve their harnesses while interacting with each other?
5. What happens if the evaluator's definition of success shifts over time (e.g., company policy changes)—can the harness gracefully adapt or does it need a reset?
6. Can the state graph and episodic memory be interpreted and audited by humans for safety and fairness before deployment updates?

## Key Takeaway
LLM agents can now learn and refine their interaction workflows after each task, fixing recurring failures without retraining the model.
