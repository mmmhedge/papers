# DataOrchestra: Learning to Orchestrate Per-Example Curation of Pretraining Data

**Authors:** Zhen Huang, Yikun Wang, Shijie Xia, Pengfei Liu
**Published:** 2026-07-27 | **arXiv:** [2607.24717v1](http://arxiv.org/abs/2607.24717v1)

## Summary
This paper presents DataOrchestra, a framework that customizes data preprocessing for each example during LLM pretraining, rather than applying fixed processing rules uniformly across all data. The system decides for each chunk whether to drop it, leave it alone, or clean it using one of several operations (programmatic editing or LLM-based rewriting), and consistently improves downstream task performance compared to using any single processing method alone.

## Theoretical Background
LLM pretraining quality depends heavily on the quality and composition of training data. Prior work has explored data filtering, deduplication, and cleaning at the corpus or domain level — but these approaches typically define one strategy and apply it everywhere. The paper builds on the intuition that different examples have different processing needs: some may need grammatical fixes, others semantic clarification, others should be discarded entirely. This connects to broader ideas in curriculum learning and adaptive training, where the treatment of examples varies based on their characteristics.

## Core Contributions
1. **Per-example curation framework**: Introduces an "orchestrator" that makes example-specific decisions (drop/keep/clean) rather than applying corpus-wide rules.
2. **Flexible operation chaining**: For chunks marked for cleaning, the system selects and chains multiple operations (programmatic editing, rule-based rewriting, or LLM-based instruction-driven rewriting) with generated concrete instructions.
3. **Empirical validation at scale**: Demonstrates consistent gains across 11 benchmarks when pretraining 0.5B–7B models from scratch on web data, plus effectiveness on math-focused continued pretraining.
4. **Computational efficiency**: Reduces processing cost by skipping unnecessary operations for examples that don't need them.

## Connections to Other Work
This relates to [[data filtering]] and [[data curation]] traditions in NLP, but inverts the typical approach: instead of defining rules upfront, it learns to route each example through a processing pipeline. It also echoes ideas from [[curriculum learning]] (adapting training based on example difficulty) and [[reinforcement learning]] for sequence decision-making (the orchestrator could be trained as a policy). The use of LLM-based rewriting connects to recent work on using language models as data processors and synthetic data generators.

## Practical Applications
1. **Production LLM training pipelines**: Companies training custom LLMs (enterprise, specialized domains) can use DataOrchestra to improve data quality without manual rule engineering.
2. **Data cleaning at scale**: Organizations with noisy web-crawled or user-generated text can apply adaptive cleaning rather than one-size-fits-all approaches.
3. **Multilingual and low-resource LLM training**: For languages with limited high-quality data, adaptive curation can extract more value from available sources.
4. **Domain-specific continued pretraining**: Fine-tuning on specialized corpora (medical, legal, scientific) where data quality varies within the domain.

## Product & Startup Ideas
1. **DataOrchestra-as-a-Service**: A hosted API that accepts raw text dumps and returns curated pretraining datasets, with configurable operations and per-example routing logic.
2. **LLM Data Marketplace**: A platform where users can upload raw datasets and an orchestrator automatically improves them, making them more valuable for resale to model-training teams.
3. **Synthetic Data Generation for Imbalanced Domains**: Use DataOrchestra to identify under-represented examples and intelligently rewrite or augment them, creating balanced training corpora.
4. **Enterprise Data Pipeline Tool**: SaaS product that integrates into LLM training workflows, continuously monitors data quality per-example, and applies targeted cleaning without manual intervention.
5. **Auto-curriculum Builder**: A tool that learns optimal example-level processing strategies for specific downstream tasks, then sells pre-optimized processing pipelines to other teams.

## Technical Limitations
1. **Orchestrator design unclear**: The paper doesn't fully specify how the orchestrator itself is trained or optimized — is it learned end-to-end, heuristic-based, or reinforcement-learning-based? This is critical but underspecified.
2. **Computational overhead**: While the system skips unnecessary operations, the orchestrator itself (likely an LLM) must run on every example, which could be expensive and may negate savings.
3. **Generalization across domains**: Training an orchestrator on one dataset may not transfer to different data distributions; retraining on new domains could be costly.
4. **Instruction quality**: The quality of automatically generated instructions for downstream tools is not validated — bad instructions could degrade data.
5. **Scalability to very large pretraining runs**: Most experiments are 0.5B–7B models; unclear if gains hold for 100B+ parameter models or massive datasets.
6. **No ablation on orchestrator complexity**: Missing clear ablations on how much the gain comes from adaptive routing vs. the specific operations themselves.

## Open Questions
1. How is the orchestrator trained or optimized? Is it learned jointly with the pretraining objective, trained separately, or heuristic-based?
2. What is the computational cost of running the orchestrator per-example, and how does it compare to the savings from skipping operations?
3. Does the orchestrator's behavior generalize to new domains, or does it need retraining?
4. How sensitive is the approach to the quality of the operation tools (the LLM-based rewriters, programmatic editors)?
5. Would end-to-end learning of the orchestrator + language model jointly outperform the current two-stage approach?
6. How does DataOrchestra compare to more recent data-centric methods like [[data valuation]] or [[influence functions]] for identifying which examples matter most?

## Key Takeaway
Customizing data processing for each example, rather than applying one strategy uniformly, consistently improves LLM pretraining performance across diverse benchmarks.
