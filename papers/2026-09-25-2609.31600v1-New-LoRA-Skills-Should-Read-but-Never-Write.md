# New LoRA Skills Should Read but Never Write

**Authors:** Zeyan Li, Panqi Yang, Qirong Guo, Shengda Zhuo, SIyuan Qiu et al.
**Published:** 2026-09-25 | **arXiv:** [2609.31600v1](http://arxiv.org/abs/2609.31600v1)

## Summary
This paper solves the problem of combining multiple fine-tuned language model adapters (LoRA modules) without performance degradation. The key insight is that adapter factorizations and coupling directions matter when composing skills — the authors introduce READ, a method that fixes both by rewriting adapters into canonical form and enforcing one-directional coupling so new skills can read but not interfere with old ones.

## Theoretical Background
Low-rank adapters (LoRA) are a parameter-efficient fine-tuning technique where instead of updating all weights of a large language model, you train small low-rank matrices that are added to the original weights. When you train multiple LoRA modules independently (one per task), merging them naively causes interference — the adapters' updates conflict in weight space. Prior composition methods either merge weights (causing interference), retrain everything (expensive), or route between separate adapters (loses the single-model goal). The paper's core insight is that a low-rank factorization W = U·V^T isn't unique — infinitely many (U, V) pairs produce the same W. This ambiguity is invisible when an adapter works alone but critical when combining adapters, because different factorizations expose different input/output subspaces that other adapters can interact with.

## Core Contributions
1. **Canonical form for LoRA**: Reformulates each adapter into a "balanced" factorization that uniquely represents the update while preserving exact behavior. This removes hidden degrees of freedom that cause composition problems.

2. **One-directional coupling**: Introduces an asymmetric composition mechanism where new skills only read from old adapters' input subspaces but cannot write to their outputs. This prevents old skills from losing their learned computation.

3. **READ algorithm**: A simple, training-efficient method where only the new skill's row of the coupling matrix is trainable; the composed update folds losslessly into base weights at inference time with zero cost.

4. **Empirical validation**: Demonstrates consistent, substantial improvements across SuperGLUE (+20 points), domain benchmarks (+7 points), and other suites when sequentially adding skills — outperforming published baselines.

## Connections to Other Work
This work relates to the broader problem of [[multi-task learning]] in language models and modular neural networks. It connects to [[parameter-efficient fine-tuning]] literature (LoRA, adapters) and the challenge of catastrophic forgetting when learning multiple tasks. The insight about factorization non-uniqueness parallels work in linear algebra and matrix decomposition, and the directional coupling resembles read/write access control in systems design. The sequential composition setting differs from recent work on simultaneous adapter merging (e.g., AdapterFusion, which requires all tasks upfront).

## Practical Applications
- **Multi-domain LLM deployment**: A single model serving multiple specialized tasks (customer support, content generation, coding assistance) without retraining or routing overhead.
- **Continual learning systems**: Adding new capabilities to production models over time without degrading existing skills (e.g., adding new languages or domains to a deployed chatbot).
- **Cost-efficient model scaling**: Organizations can accumulate task-specific skills cheaply via LoRA, then compose them into one efficient model for inference.
- **Personalization**: Learning user-specific adapters that compose into a personalized model without separate model instances.

## Product & Startup Ideas
1. **Multi-skill LLM orchestration platform**: SaaS that manages composition of LoRA adapters for enterprises — train once per task, auto-compose and deploy with guaranteed old-skill preservation. Target: companies with multiple LLM use cases.

2. **Adapter marketplace**: A registry where teams contribute fine-tuned LoRA modules (e.g., medical domain, legal expertise, domain-specific terminology) that can be securely composed and licensed. Buyers compose without retraining.

3. **Continuous model evolution tool**: Infrastructure that tracks which skills are added in what order, versioning composed models and enabling rollback if a new skill degrades performance — focus on regulated industries (finance, healthcare).

4. **Domain-specific LLM builder**: No-code/low-code platform where non-ML users upload datasets, the system trains minimal LoRA adapters, and automatically composes them into domain-specific models using READ.

5. **Model surgery service**: Consulting/API service that takes an existing fine-tuned LLM and a new task, uses READ to add new capabilities while provably preserving old ones — useful for legacy model upgrade scenarios.

## Technical Limitations
- **Assumes independent training**: Adapters must be trained independently first; if tasks have pre-existing dependencies, this may waste capacity. No mechanism for coordinated multi-task pre-training.
- **Sequential addition**: The method adds skills one-at-a-time; unclear how well it scales when composing many adapters (e.g., 50+ tasks) or how order sensitivity behaves.
- **Low-rank assumption**: LoRA's low-rank constraint may not suit all tasks equally; the method's benefits depend on LoRA quality per task.
- **No task interference metrics**: The paper doesn't quantify how much old skills are "reading" from new ones or provide diagnostics for detecting problematic interactions.
- **Limited theoretical guarantees**: No formal bounds on composition error or conditions under which READ is guaranteed to preserve old skill performance.
- **Evaluation scope**: Benchmarks are standard (SuperGLUE, etc.); real-world multi-task scenarios with hundreds of diverse skills are not tested.

## Open Questions
- How does READ scale to 20+ or 100+ composed adapters? Does composition order matter critically, and is there a principled order for adding skills?
- Can you reverse the coupling direction (new skills write, old read) and what breaks? Does READ work for heterogeneous adapter types (not just LoRA)?
- What is the theoretical limit on how many skills can be composed before the coupling matrix becomes rank-deficient or loses expressivity?
- Can you automatically detect when a new skill's coupling should be added vs. when retraining from scratch is better?
- Does READ work with other parameter-efficient methods (prefix-tuning, adapters, prompt tuning) or is the factorization insight unique to LoRA?
- In a real production system, how would you handle the problem of deciding the order in which to add new skills without costly recomposition?

## Key Takeaway
Composing multiple fine-tuned adapters works when new skills read old skill subspaces but never overwrite them.
