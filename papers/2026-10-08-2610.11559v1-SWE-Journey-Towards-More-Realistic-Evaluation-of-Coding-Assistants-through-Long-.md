# SWE-Journey: Towards More Realistic Evaluation of Coding Assistants through Long-Horizon, Multi-Turn Interaction

**Authors:** Hexuan Deng, Yue Wang, Wenyu Jiang, Cheng Yang, Haolin Yang et al.
**Published:** 2026-10-08 | **arXiv:** [2610.11559v1](http://arxiv.org/abs/2610.11559v1)

## Summary
This paper introduces SWE-Journey, a benchmark that evaluates coding assistants (AI agents that help write code) in more realistic scenarios — long sequences of development tasks and multi-turn conversations with users. Current benchmarks test isolated, simple coding problems, but real developers interact with AI repeatedly over hours, clarifying requirements and fixing bugs. The paper shows that current coding assistants work well with expert users but fail frequently with non-coders, revealing a critical gap in reliability.

## Theoretical Background
This work builds on two major areas: (1) **LLM agents** — language models that take actions (like writing code) and respond to feedback in loops — and (2) **benchmark design** for evaluating AI systems. Prior work (like SWE-bench) evaluates coding ability on isolated GitHub issues, but doesn't capture the iterative, conversational nature of real development. The paper's key insight is that coding assistance is fundamentally a **multi-agent interaction problem**: the AI agent, the human user, and the evolving codebase form a system that must coordinate over many turns. The authors ground their benchmark in user-simulation techniques, where synthetic agents mimic real developer behavior to create repeatable test scenarios.

## Core Contributions
1. **Task-horizon synthesis pipeline**: An automated method to generate long-horizon coding tasks (multi-step problems spanning full development cycles) from short GitHub issues, addressing the unrealism of current isolated-problem benchmarks.
2. **User-persona simulation**: Mining four representative user personas (architect, experienced coder, junior coder, non-coder) from real interaction logs, then building agents that simulate realistic multi-turn conversations with coding assistants.
3. **Performance stratification**: Empirical finding that coding assistant success varies dramatically by user type (75% task pass-rate with architects vs. <25% with non-coders), exposing accessibility and reliability gaps not captured by existing benchmarks.
4. **Capability taxonomy**: Identifying "asking right, finding right, fixing right" as three key competencies required during agent–human interaction, providing a diagnostic lens for failure analysis.

## Connections to Other Work
This paper extends [[SWE-bench]], the standard for evaluating coding AI, by adding temporal and conversational depth. It relates to broader work on **[[RLHF]]** (reinforcement learning from human feedback) and **interactive AI systems**, where agents learn from user corrections. The multi-agent framing connects to [[multi-agent-systems]] research, where heterogeneous agents (human + AI) must collaborate. The work also touches on **agent reliability and alignment** — non-coders represent a less-expert user base, so the performance drop signals a misalignment between assistant design (optimized for expert developers) and real-world deployment scenarios.

## Practical Applications
1. **Coding assistant product development**: Companies building AI coding tools (GitHub Copilot, Claude, JetBrains AI Assistant) can use SWE-Journey to stress-test their systems on realistic workflows before release, catching failure modes that isolated benchmarks miss.
2. **Enterprise software quality assurance**: Organizations deploying coding assistants to junior or non-technical teams can validate that the tool is safe and reliable for that population before full rollout.
3. **User-adaptive coding assistants**: Products can dynamically adjust explanation depth, confirmation prompts, and error messages based on detected user expertise level, using persona classification to improve helpfulness.
4. **Coding education and pair-programming**: Educational platforms can use persona-based interaction data to calibrate AI tutors that scaffold learning for students at different levels.
5. **Internal developer tooling**: Large companies can run SWE-Journey variants on their own codebases and user bases to benchmark internal coding assistants.

## Product & Startup Ideas
1. **CodeReliability.ai** — A benchmarking-as-a-service platform where coding tool vendors upload their assistants and get scored against SWE-Journey scenarios, segmented by user persona; publish results to help teams choose the right tool.
2. **AdaptiveCodeAssistant** — A coding IDE plugin that detects user expertise (junior vs. senior) via interaction patterns and dynamically recalibrates prompts, explanations, and UI to match competence level.
3. **EngineeringTeamAnalytics** — Track coding assistant effectiveness per team member using the "asking/finding/fixing" diagnostic framework; identify bottlenecks (e.g., "team struggles with fix-right") and recommend training or tool tweaks.
4. **NonCoderCoding** — A no-code/low-code platform specifically optimized for non-technical users interacting with AI, using SWE-Journey insights to surface the simplest, most guided interaction flows.
5. **CodingAssistantQA** — Automated testing service that runs your internal or third-party coding assistant through long-horizon, multi-turn scenarios (tailored to your codebase) to certify it's production-safe for junior developers.

## Technical Limitations
1. **Persona synthesis validity**: The four personas are mined from existing data; they may not generalize to other domains (e.g., scientific computing, embedded systems) or geographies with different developer populations.
2. **Simulation fidelity**: User-simulation agents may not capture the full complexity of real human behavior—patience, frustration, domain expertise shifts, or strategic exploration that real developers exhibit.
3. **Repository diversity**: The benchmark likely draws from a specific slice of GitHub (e.g., web/backend-heavy); results may not transfer to systems programming, hardware design, or specialized domains.
4. **Evaluation metric opacity**: Pass rates on "requested functionality" are crude; the paper doesn't deeply probe partial correctness, security flaws, or code quality (performance, maintainability), which matter in production.
5. **Scalability**: Constructing and running long-horizon multi-turn scenarios is computationally expensive; unclear whether the benchmark can scale to thousands of tasks or continuous integration pipelines.
6. **Causality in failure**: The paper identifies persona-linked performance gaps but doesn't systematically ablate which capability deficits (asking/finding/fixing) drive the gaps, making root-cause analysis incomplete.

## Open Questions
1. **Persona transferability**: Do these four personas replicate across different programming languages, domains, or company cultures? Would hiring a tenth persona reveal new failure modes?
2. **Agent-specific weaknesses**: Which coding assistants (Claude, Copilot, Codex, open-source models) struggle most with which persona-capability pairs? Can we map fine-grained recommendations?
3. **Improvement pathways**: If we fine-tune or prompt-engineer a coding assistant specifically to improve "asking right" for non-coders, does it generalize to other personas and capabilities?
4. **Long-term interaction effects**: Do multi-turn interactions improve as the agent learns the user's style, codebase context, and preferences? How should benchmarks account for adaptation over time?
5. **Hybrid human-AI strategies**: When a non-coder fails with a pure AI assistant, what combination of simplified UI, scaffolding, or human-in-the-loop intervention would restore reliability?
6. **Production correctness**: Beyond test pass-rates, does the benchmark or follow-up work measure security flaws, runtime errors, or technical debt introduced by AI-assisted code?

## Key Takeaway
Current coding assistants work well for expert developers but fail frequently with non-coders in realistic multi-turn tasks, revealing a reliability gap that isolated benchmarks miss.
