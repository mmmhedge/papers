# InterSAGE: The Secure and Verifiable Interoperability Protocol for An Internet of Agents

**Authors:** Zhenhua Zou, Sheng Guo, Qiuyang Zhan, Lepeng Zhao, Shuo Li et al.
**Published:** 2026-08-13 | **arXiv:** [2608.13030v1](http://arxiv.org/abs/2608.13030v1)

## Summary
InterSAGE is a security protocol suite that enables LLM-powered agents to safely interact across organizational boundaries—proving their identity, capabilities, and accountability. It fills a critical gap in agent interoperability: existing communication protocols define how agents talk, but not how they establish trust or prove what they're authorized to do.

## Theoretical Background
The paper builds on several mature foundations: decentralized identity (DIDs — distributed identifiers that don't require a central authority), verifiable credentials (cryptographic proofs of attributes), zero-trust security (assuming no actor is inherently trustworthy), and delegation frameworks (allowing one agent to grant another permission to act on its behalf). It also references established communication protocol layers (like MCP, A2A, ANP) that handle agent-to-agent messaging. The core novelty is recognizing that trust—not just communication—needs to be a first-class protocol layer for agent ecosystems to work safely at scale.

## Core Contributions
1. **Four-layer trust architecture**: Persistent Identity, Discovery, Trust Negotiation, and Accountability as orthogonal to (not embedded in) communication protocols.
2. **Agent Identity Cards**: Cryptographic bindings of developer, code package, operator, and deployment context—enabling persistent, verifiable identity across agent lifecycles.
3. **Capability-aware discovery**: Using DID-bound Verifiable Credentials so agents can advertise and discover what they're actually authorized to do, not just what capabilities they technically have.
4. **Monotonic capability attenuation**: A two-tier access control model where delegated permissions can only shrink (never grow), preventing privilege escalation.
5. **Kernel-mediated audit trails**: Immutable logs of usage, delegation, and execution bound to agent identity *without requiring a blockchain*, making accountability practical and lightweight.
6. **Comprehensive comparative analysis**: Systematic evaluation against 50+ prior efforts in agent protocols, identity systems, OAuth extensions, and audit architectures, showing no existing system addresses all four layers jointly.

## Connections to Other Work
InterSAGE complements rather than replaces existing agent communication protocols ([[MCP]], A2A, ANP, AG-UI). It's related to OAuth/OIDC but extends them for multi-agent delegation contexts. The work draws inspiration from zero-trust governance (principle of least privilege) and decentralized identity frameworks but applies them specifically to autonomous agent ecosystems. It contrasts with blockchain-based audit systems (like those using consensus ledgers) by proving accountability through kernel-level cryptography—more practical for high-frequency inter-agent interactions.

## Practical Applications
1. **Enterprise agent marketplaces**: Organizations running multiple internal agents (document analysis, scheduling, procurement) need to audit who delegated what to whom—InterSAGE makes this cryptographically verifiable.
2. **Cross-organizational task delegation**: A supply-chain agent from Company A invoking a logistics agent from Company B can prove its authorization and bind the outcome to both parties' records.
3. **Regulatory compliance**: Financial services, healthcare, or government agencies running autonomous systems need immutable proof of what decisions were made, by which agent, under whose authority—InterSAGE provides this without a centralized audit server.
4. **Agent-as-a-service platforms**: Marketplaces where developers publish agents need to prevent impersonation, capability inflation, and unaccountable delegation.
5. **Robotic process automation (RPA) with verifiable handoffs**: In high-trust domains, automating workflows across departments requires proof that each step was performed by the intended agent.

## Product & Startup Ideas
1. **Agent Identity Provider (as-a-service)**: A hosted platform that issues and manages Agent Identity Cards, capability manifests, and audit trail storage for enterprise customers—similar to how auth0 handles identity for web apps, but for autonomous agents.
2. **InterSAGE-compliant agent marketplace**: A curated platform where organizations publish trusted agents (with cryptographically verified capabilities and audit history), allowing seamless secure composition across teams.
3. **Compliance audit platform for autonomous systems**: Specialized software for regulated industries that ingests InterSAGE audit trails and generates regulatory reports (SOX, HIPAA, etc.) automatically.
4. **Zero-trust agent orchestration engine**: A control-plane product that enforces InterSAGE policies across heterogeneous agents in legacy enterprise environments, bridging old APIs with new agent protocols.
5. **Multi-tenant agent sandbox with built-in InterSAGE enforcement**: A containerized execution environment where agents run with kernel-mediated audit trails and capability attenuation baked in—reducing adoption friction for enterprises.

## Technical Limitations
1. **Kernel-level deployment assumption**: The audit trail mechanism assumes agents can run in contexts with kernel-mediated cryptography. In fully sandboxed or third-party-hosted environments (e.g., Function-as-a-Service), this may not apply.
2. **Identity bootstrapping**: The paper doesn't deeply address the initial trust problem—how does a new agent obtain an identity card that stakeholders actually accept? Real-world adoption may require external root-of-trust mechanisms (certificate authorities, federation).
3. **Capability expression semantics**: The protocol defines the structure of capability manifests but doesn't solve the hard problem of expressing *semantic* capabilities unambiguously (e.g., what does "can read user data" actually permit across different schemas?).
4. **Performance overhead**: No benchmarks provided. Cryptographic verification of delegation chains, audit trails, and capability checking at every inter-agent call could introduce latency that's prohibitive for real-time agent swarms.
5. **Legacy protocol integration**: While claimed to complement MCP, A2A, etc., the paper doesn't detail the engineering effort required to retrofit InterSAGE into existing deployed agent systems.
6. **Revocation without consensus**: Revoking an agent's capabilities requires out-of-band coordination (no ledger), which may be slow in distributed settings or create short windows of inconsistent state.

## Open Questions
1. **Capability expression standard**: What ontology or schema should be standardized for expressing agent capabilities in a way that's both machine-checkable and human-auditable?
2. **Performance at scale**: How do audit trail lookups, capability verification, and monotonic attenuation affect latency in agent graphs with hundreds of delegation hops?
3. **Revocation semantics**: What's the optimal strategy for revoking an agent's capabilities or identity in a distributed system without a consensus layer? How long can revocation take before it creates a security risk?
4. **Developer experience**: How would typical agent developers interact with InterSAGE? What tooling, SDKs, or policies reduce friction without sacrificing security guarantees?
5. **Formal verification**: Can the monotonic attenuation and audit-trail binding properties be formally proven against a threat model? Are there subtly exploitable corner cases?
6. **Adoption catalysts**: Which industries or use cases should be targeted first to prove InterSAGE's value and create momentum?

## Key Takeaway
InterSAGE adds a cryptographic trust layer for agent-to-agent interactions, proving identity and accountability without relying on blockchains or centralized authorities.
