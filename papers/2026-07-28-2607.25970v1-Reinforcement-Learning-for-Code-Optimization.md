# Reinforcement Learning for Code Optimization

**Authors:** Pierre Chambon, Kunhao Zheng, Juliette Decugis, Benoit Sagot, Gabriel Synnaeve
**Published:** 2026-07-28 | **arXiv:** [2607.25970v1](http://arxiv.org/abs/2607.25970v1)

## Summary
This paper tackles code optimization using reinforcement learning — training neural networks to generate faster programs, not just correct ones. The core insight is that naive RL fails when optimizing for execution speed due to noisy timing measurements and reward sparsity; the authors solve this by carefully designing how code is tested, how speed feeds into rewards, and how the learning algorithm handles sparse noisy signals. On benchmark problems, their approach roughly doubles the percentage of solutions that achieve significant speedups while maintaining correctness.

## Theoretical Background
Prior work has established [[RLHF|RL for code correctness]] — generate code, test it against hidden cases, reward passes. Execution time as a reward signal seems natural but conflicts with two fundamental challenges in RL: sparse rewards (speed improvements may be rare) and measurement noise (timing varies due to hardware, caching, OS scheduling). The paper builds on [[GRPO]] (a group relative policy optimization variant), standard RL algorithms for code generation, and the empirical observation that combining multiple objectives in reward design is unstable when signals have different scales and noise levels.

## Core Contributions
1. **DMC-Optim benchmark**: Large-scale optimization test suite with careful sandbox calibration for reliable timing measurement — not just measuring raw wall-clock time but accounting for environment variance.
2. **Learnable execution time reward**: Proposes composing correctness and speed explicitly within the RL environment (not as separate objectives), and uses an offline simulator to predict which code configurations are most promising before full evaluation.
3. **Robust GRPO adaptation**: Modifies the GRPO algorithm and its evaluation procedure to handle the sparser, noisier reward landscape of timed execution — specifically addressing instability that emerges when timing drives the signal.
4. **Empirical validation**: Shows strict improvements on pass@1 (correctness + speed): 18.0% → 31.3% for Qwen 2.5 7B, 30.7% → 50.4% for CWM 32B, with up to 125% relative gains at stricter speed thresholds.

## Connections to Other Work
This work extends the established pipeline of [[RLHF]] and RL-for-code-generation (e.g., Codeforces benchmarks) into the optimization regime. It shares DNA with multi-objective RL and curriculum learning (the simulator acts as a learned curriculum hint). The offline simulator approach echoes model-based RL and reward modeling techniques. The paper's emphasis on measurement reliability and reward composition connects to broader discussions in [[alignment]] about reward specification when signals conflict.

## Practical Applications
1. **Compiler optimization automation**: Generate optimized code variants for performance-critical sections (scientific computing, game engines, ML inference kernels).
2. **Code review and refactoring suggestions**: Identify and suggest algorithmic improvements in production codebases, flagged for human review.
3. **Competitive programming coaching**: Assist contestants in optimizing solutions under strict runtime constraints.
4. **Embedded systems code generation**: Optimize for limited memory/power budgets where human effort is high.
5. **Cloud infrastructure cost reduction**: Auto-optimize user-submitted code to reduce execution costs on metered platforms.

## Product & Startup Ideas
1. **CodeSpeed.ai**: B2B SaaS that ingests a codebase, identifies slow hot paths, generates optimized variants using this RL approach, and flags safe replacements for review—monetize on lines-of-code or performance improvements achieved.
2. **OptimizeHub**: GitHub integration that runs this RL system on PRs and comments with "this could be 2.3x faster" suggestions, with one-click diffs; freemium model (free for open-source, paid for private repos).
3. **CompetitiveEdge**: Coaching platform for coding contests; uses this system to generate optimized solutions and explain the trade-offs (correctness vs. speed vs. complexity); subscription model.
4. **EmbeddedOptim**: Specialized IDE plugin for firmware/embedded development; auto-suggests memory-efficient and faster code, tuned for specific microcontroller constraints.
5. **MLOps optimizer**: Integrate into ML pipelines to auto-optimize inference code (data loading, preprocessing, model prediction kernels) before deployment; charge per optimization job or per savings achieved.

## Technical Limitations
1. **Relative to human optimization**: The paper reports CWM 32B reaches only ~50% of the human rate of complexity-class improvements (14% vs. 28%), so it is not a replacement for expert optimization.
2. **Sandbox assumptions**: Relies on reliable, calibrated timing measurement; degrades when the sandbox is unstable or diverges from production hardware (the paper shows 100–200% relative improvement when sandbox is degraded, implying heavy dependency).
3. **Scalability to large codebases**: Evaluated on algorithmic coding problems; unclear how this scales to real-world production code with complex dependencies, external libraries, and distributed systems.
4. **Correctness preservation**: While the method preserves pure-correctness scores, there is no formal guarantee that an optimization-driven RL step won't introduce latent bugs or edge-case regressions.
5. **Generalization across hardware**: Training and test environments may differ (GPU vs. CPU, cache sizes, OS overhead); results may not transfer across devices.

## Open Questions
1. How does performance scale to problems with very long execution times or where small relative improvements matter most?
2. Can the offline simulator component be improved (e.g., with learned predictors) to further reduce the cost of expensive timing measurements?
3. Does this approach generalize to code with external dependencies (database calls, network I/O, library calls) where timing is less deterministic?
4. How should the method handle multi-threaded or GPU-accelerated code where timing and correctness interact in complex ways?
5. Can interpretability techniques reveal what algorithmic patterns the RL model learns to apply (e.g., does it consistently discover loop unrolling, memoization, etc.)?

## Key Takeaway
RL can optimize code for speed by carefully measuring timing, composing rewards, and adapting the learning algorithm to sparse noisy signals.
