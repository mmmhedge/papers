# Agent Name Collision Attacks in Multi-Agent Systems

**Authors:** Adithyan Arun Kumar
**Published:** 2026-09-23 | **arXiv:** [2609.27624v1](http://arxiv.org/abs/2609.27624v1)

## Summary
This paper identifies a class of security vulnerabilities in multi-agent systems where hosts incorrectly use agent names (human-readable metadata) as routing identifiers, enabling attackers to impersonate trusted agents. The authors demonstrate that six out of seven tested implementations are vulnerable to "wrong-peer dispatch" attacks, where requests meant for a trusted agent can be routed to an attacker-controlled peer instead—a practical security failure that doesn't require exploiting the protocol itself, only implementation mistakes.

## Theoretical Background
Multi-agent systems rely on distributed agent orchestration where remote agents (represented as "Agent Cards") are converted into local agents, tools, and routing targets. The A2A protocol specifies agent names as human-readable metadata for presentation rather than as cryptographically bound identities. Secure routing in distributed systems typically requires stable, origin-bound identifiers (e.g., cryptographic keys or UUIDs) separate from display names. The paper builds on fundamental principles from network security and message routing: name collisions and ambiguous identifiers have historically caused misdirection attacks in RPC systems, DNS, and service meshes. The key insight is that **names alone are insufficient for routing security**—without explicit collision semantics or identity binding, implementations naturally but unsafely fall back to name-based dispatch.

## Core Contributions
1. **Systematic vulnerability class identification**: Demonstrates a recurring implementation pattern where name-based routing creates wrong-peer dispatch, not a monolithic protocol flaw.
2. **Empirical testing across seven implementations**: Shows that six client-style integrations and one broker-based system exhibit the vulnerability, with different failure modes (interception, denial-of-service).
3. **Careful scope delineation**: Proves the vulnerability is NOT a universal A2A exploit and does NOT automatically transfer credentials or tools—success depends on deployment configuration and what the attacker-controlled peer can consume.
4. **Prescriptive remediation**: Establishes clear responsibility assignment: protocol must define collision semantics, implementations must use origin-bound identities, and deployments must reject ambiguous aliases.

## Connections to Other Work
This relates to broader **multi-agent coordination security** challenges (similar to issues in [[MARL]] systems and distributed agent frameworks), name-based routing vulnerabilities in legacy RPC and middleware systems, and the general problem of **identity vs. naming** in distributed systems. It echoes lessons from DNS hijacking, service mesh misconfiguration (e.g., Kubernetes service discovery attacks), and OAuth/OIDC redirect-based attacks where human-readable identifiers are confused with cryptographic identity. The work complements research on **agent sandboxing** and **capability delegation** in multi-agent environments.

## Practical Applications
1. **Multi-agent LLM orchestration platforms** (e.g., agent swarms, tool-calling frameworks): Critical to audit routing logic and enforce origin-bound identities to prevent tool misuse or data exfiltration.
2. **Microservice brokers and workflow engines** (e.g., Kubernetes operators, serverless function orchestration): Must enforce stable identity binding in dispatch logic.
3. **Distributed AI model serving**: When multiple model endpoints are exposed to a broker or router, name collisions could route inference requests to adversarial or compromised models.
4. **Enterprise agent frameworks** (e.g., RPA, chatbot platforms): Prevents unauthorized agents from intercepting requests meant for privileged system agents.

## Product & Startup Ideas
1. **Agent Identity & Routing Audit Service**: SaaS tool that scans multi-agent deployments for name-collision vulnerabilities, tests routing under adversarial conditions, and generates compliance reports.
2. **Secure Agent Routing Middleware**: Drop-in proxy/sidecar that enforces cryptographic identity binding and rejects ambiguous agent names before dispatch.
3. **Multi-Agent Security Testing Framework**: Open-source or commercial suite for regression testing agent implementations against name collision, wrong-peer, and credential-leakage scenarios.
4. **Agent Supply Chain Verification Platform**: Registry + deployment tool that cryptographically binds agent identities to source, preventing name-squatting and spoofing in federated agent networks.
5. **Zero-Trust Agent Mesh**: Extension of service mesh concepts (e.g., Istio) specifically for multi-agent systems, with built-in mutual TLS, identity verification, and immutable routing tables.

## Technical Limitations
1. **Scope is implementation-focused, not protocol-exhaustive**: The paper tests seven specific implementations but doesn't formally verify the A2A protocol itself—new implementations may or may not be vulnerable.
2. **No automated detection method**: The findings require manual code review or targeted regression testing; no static analysis tool or automated fuzzing methodology is provided.
3. **Deployment-dependent impact**: The actual harm (credential transfer, tool access) varies by configuration—the paper correctly notes this but doesn't provide a risk scoring matrix for different deployment patterns.
4. **Doesn't address identity binding mechanisms**: The paper prescribes origin-bound identities but doesn't specify *how* (TLS certificates? cryptographic signatures? DHT-backed keys?) or evaluate performance/usability tradeoffs of different schemes.
5. **Limited to synchronous request-response and brokered patterns**: Unclear if asynchronous messaging, pub-sub, or peer-to-peer agent discovery patterns have analogous vulnerabilities.

## Open Questions
1. How do name-collision attacks interact with **agent authentication** (e.g., mutual TLS, mTLS)? Can TLS prevent this entirely, or is there a window before cert verification?
2. What is the attack surface in **federated multi-agent systems** where agents from different organizations coexist in a shared broker? Is reputation-based routing (e.g., trust scores) a viable defense?
3. Can this vulnerability be **automatically detected** at static analysis or runtime (e.g., via symbolic execution or network tap)? What is the false-positive rate?
4. How do name collisions propagate in **hierarchical or delegated agent architectures** where agents themselves spawn sub-agents?
5. What is the relationship to **agent capability attestation** and **zero-knowledge proofs** of agent identity—could these strengthen routing security?

## Key Takeaway
Name-based routing in multi-agent systems enables wrong-peer dispatch attacks; implementations must use cryptographically bound identities, not human-readable names, for dispatch decisions.
