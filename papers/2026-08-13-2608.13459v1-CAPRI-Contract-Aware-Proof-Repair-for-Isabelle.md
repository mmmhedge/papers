# CAPRI: Contract-Aware Proof Repair for Isabelle

**Authors:** Jim Woodcock, Gabriel Leite, Augusto Sampaio, Ran Wei
**Published:** 2026-08-13 | **arXiv:** [2608.13459v1](http://arxiv.org/abs/2608.13459v1)

## Summary
This paper presents CAPRI, a system for using LLMs to repair failed Isabelle proofs (formal mathematical proofs written in a proof assistant) while ensuring that LLM edits stay within authorized boundaries. The key insight is that simply checking whether Isabelle accepts a proof isn't enough — you also need to verify that the LLM didn't secretly modify parts of the code the developer didn't intend. CAPRI adds a "contract" layer that tracks exactly what changed, making the repair process auditable and safer for use in high-assurance software development.

## Theoretical Background
Isabelle is a proof assistant — software that helps humans write and verify mathematical proofs with machine-checked correctness. Traditional use relies on human expertise. Recent work has explored using LLMs to generate or repair proofs, but this creates a trust problem: if an LLM rewrites a proof and Isabelle accepts it, how do you know the LLM only changed what you asked it to? CAPRI builds on the concept of contracts (machine-readable specifications of what changes are permitted) and audit trails, borrowing ideas from software integrity and version control. The paper evaluates different "workflows" — sequences of prompting and repair strategies — ranging from one-shot generation to iterative refinement.

## Core Contributions
1. **Contract-aware repair workflow**: A framework that enforces edit boundaries via independent checking, not just Isabelle's acceptance. Prompts, proposals, hashes, and verdicts are all logged for audit.
2. **Empirical evaluation of interface design**: Demonstrates that restricting LLM access to proof bodies only (not the full theory file) eliminates contract violations while achieving comparable repair rates (29/36 vs. 31/36).
3. **Quantified safety results**: Among 144 successful repairs, only 6 violated the contract, and all violations came from unrestricted workflows. This provides hard data on the trade-off between capability and safety.
4. **Statistical rigor**: Uses exact McNemar tests on 180 runs across multiple prompting strategies and LLM backends (OpenAI, Sol, OpenRouter), avoiding overconfident claims about small differences.

## Connections to Other Work
This work sits at the intersection of [[large-language-models]] for code generation, formal verification, and AI safety. It relates to:
- **Proof automation**: Prior work used neural networks for premise selection in theorem proving, but CAPRI focuses on repair given a failed proof.
- **LLM alignment and oversight**: Parallels concerns in [[RLHF]] and interpretability — the problem of ensuring an autonomous system doesn't exceed its mandate. CAPRI's contract model is a lightweight governance mechanism.

## Practical Applications
1. **Proof maintenance in large software projects**: When proof libraries evolve (e.g., Isabelle updates), LLMs can help repair broken proofs, but developers need proof that edits are contained.
2. **Formal methods for critical systems**: Aerospace, medical devices, and cryptography rely on formally verified code; CAPRI enables faster proof repair without sacrificing assurance.
3. **Interactive theorem proving workflows**: Proof engineers can use CAPRI as an IDE plugin, getting LLM suggestions while maintaining an immutable audit log.
4. **Educational tools**: Students learning formal proofs can get hints from LLMs without worrying that suggestions will rewrite the entire proof file.

## Product & Startup Ideas
1. **Proof-as-a-Service platform**: A cloud service that takes a failed Isabelle proof, applies CAPRI-style repairs, and returns a cryptographically signed, auditable result for mission-critical codebases.
2. **IDE plugin for Isabelle/VS Code**: Real-time LLM-powered proof suggestions with visual diff and contract violation warnings; charges per repair or subscription.
3. **Formal verification SaaS for smart contracts**: Use CAPRI to repair proofs of Ethereum smart contract correctness, addressing the audit and liability concerns of DeFi platforms.
4. **Proof library maintenance service**: Offer to update and maintain formally verified code libraries as dependencies change, with CAPRI enforcing that only proofs are touched.
5. **Governance-as-code for proof automation**: Sell templates and monitoring tools that let enterprises define and enforce proof-repair policies (e.g., "no edits outside function lemmas") across teams.

## Technical Limitations
1. **Limited scope**: Evaluated on only 12 failed proofs across 4 projects — small sample size; results may not generalize to industrial-scale developments with thousands of proofs.
2. **No statistical significance**: Most workflow comparisons (e.g., Sol vs. OpenAI) showed no significant difference ($p=0.0625$), so claims of superiority are weak.
3. **Contract design is manual**: The paper doesn't automate how to define what edits are "authorized" — a developer must specify this upfront, which is burdensome and error-prone.
4. **Iterative workflows remain risky**: Even with contracts, iterative repair (where the LLM sees previous failures) produced contract violations; the root cause (multi-turn reasoning leading to scope creep) isn't fully diagnosed.
5. **No comparison to human baseline**: We don't know if LLM repair rates (22–33 out of 36) are better or worse than a human expert repairing proofs manually.
6. **LLM-specific results**: Findings are tied to OpenAI and Sol models circa 2026; future LLMs may behave very differently.

## Open Questions
1. **How does contract design scale?** Can you automatically infer safe edit contracts from proof structure, or must developers write them by hand for each file?
2. **Why do iterative workflows violate contracts?** What prompting strategies or architectural changes would let LLMs refine proofs without scope creep?
3. **Can you repair proofs in other proof assistants?** Coq, Lean, and Agda have different syntax and semantics — does CAPRI generalize?
4. **What's the human-LLM hybrid sweet spot?** When should a developer manually repair a proof vs. trusting CAPRI? Can you predict repair difficulty?
5. **How do contracts interact with proof search strategies?** Some proof tactics (e.g., automation) rewrite large proof blocks; can CAPRI enforce contracts without blocking legitimate tactic changes?

## Key Takeaway
LLMs can safely repair formal proofs if you restrict their edit scope and audit all changes, but iterative multi-turn repair remains risky.
