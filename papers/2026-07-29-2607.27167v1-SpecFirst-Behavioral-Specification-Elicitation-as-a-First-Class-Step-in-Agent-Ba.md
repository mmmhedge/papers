# SpecFirst: Behavioral Specification Elicitation as a First-Class Step in Agent-Based Program Synthesis from Scratch

**Authors:** Yihao Chen, Shi Chang, Feng Lin, Khaled Chawa, Boyuan Chen et al.
**Published:** 2026-07-29 | **arXiv:** [2607.27167v1](http://arxiv.org/abs/2607.27167v1)

## Summary
This paper shows that LLM-based agents struggle to write programs from scratch because they try to understand requirements and write code in one pass. The authors propose SpecFirst, a two-stage approach: first, an agent carefully explores a program's behavior and writes a formal specification; second, a different agent uses that specification to generate code. On 200 benchmark tasks, SpecFirst improves success rates by 7–21% over single-pass approaches, demonstrating that separating specification from implementation is crucial for from-scratch program synthesis.

## Theoretical Background
This work bridges two disciplines: classical software engineering (particularly requirements engineering — the practice of formally capturing what a system must do before building it) and modern LLM-based code generation. Traditional program synthesis has treated specification and implementation as intertwined or implicit; LLMs excel at code generation when given clear context and examples, but struggle with ambiguous or incomplete requirements. The paper draws on the observation that human software engineers separate requirements elicitation from implementation for good reason: ambiguity in requirements often propagates downstream and becomes expensive to fix. Recent work on [[LLM agents]] for software engineering (e.g., ProgramBench) has quantified the difficulty of from-scratch synthesis — frontier models solve fewer than 1% of cases given only documentation and a binary oracle to test against.

## Core Contributions
1. **Explicit specification phase**: SpecFirst introduces a dedicated specification elicitation stage, directly borrowed from requirements engineering, as a first-class phase before code synthesis. This is not incremental prompting or multi-turn dialogue — it is a structural separation of concerns.
2. **Two-agent decomposition**: Separates the task into a spec agent (focused on probing behavior and writing a formal specification) and a code agent (focused on implementation given a stable reference). Each agent has a clear, bounded role.
3. **Empirical validation**: Demonstrates consistent, statistically significant improvements across 200 benchmarks, four LLM models (spanning two families), and two capability scales. Improvements are substantial (6.9–21.3% test pass rate gain) and paired with deeper behavioral analysis showing earlier and more sustained code construction.
4. **Ablation of the problem**: Shows concretely that the monolithic single-pass approach loses behavioral intent as context window drifts and conflates documentation reading with implementation, causing agents to probe insufficiently.

## Connections to Other Work
This paper aligns with classical software engineering best practices (requirements engineering, specification-first design) and shows they translate effectively to the LLM agent domain. It contrasts with [[chain-of-thought]] and single-loop agent frameworks that process all subtasks in one pass. Related to [[multi-agent-systems]] in that it decomposes a complex task across specialized agents, though the agents are not competitive or cooperative in the traditional sense — they are sequential and role-specific. The work also connects to broader research on [[LLM prompting strategies]] and [[agent architecture]], suggesting that task decomposition (not just prompting cleverness) drives capability gains.

## Practical Applications
1. **IDE/Code Editor Integration**: Tools like Copilot or VSCode extensions could use a spec-first pipeline to generate code for novel utilities or scripts given only informal requirements and a test harness.
2. **Legacy System Documentation**: Reverse-engineer formal specifications from binaries or poorly documented legacy code, making it safer to refactor or extend without introducing bugs.
3. **Regulatory Compliance Code**: In finance or healthcare, generate code that must provably match a formal specification (requirements) before implementation; separating these stages reduces certification risk.
4. **Automated API Wrappers**: Given a binary API and documentation, automatically generate clean, correct client libraries by first specifying the API contract, then implementing it.
5. **Educational Software Testing**: Help students learn requirements engineering by having an agent probe a reference implementation and write a specification, then compare student implementations against it.

## Product & Startup Ideas
1. **RequirementsFirst IDE**: A development environment that enforces spec-first workflow for agents and teams; tracks specification-to-code traceability and flags divergence.
2. **Binary Behavior Auditor**: SaaS tool that uses spec agents to automatically generate formal specifications of closed-source or legacy binaries (reverse-engineering from behavior), enabling compliance checks and security audits.
3. **Code Generation API**: Hosted service that wraps SpecFirst as an API; users submit documentation + binary/test harness, get specification + code; sell per-call or subscription.
4. **Spec-to-Implementation Validator**: CI/CD plugin that validates generated code against auto-derived specifications; prevents drift and catches early misinterpretations before they accumulate.
5. **Requirements Mining for Refactoring**: Tool that extracts and formalizes hidden specifications from existing code, enabling safer, data-driven refactoring and modernization of legacy systems.

## Technical Limitations
1. **Binary Oracle Dependency**: SpecFirst requires an executable binary or test harness to explore behavior. In domains without executable artifacts (e.g., physical hardware, distributed systems), this approach is inapplicable.
2. **Specification Fidelity**: The spec agent must write a specification that is both complete and precise. Incomplete or incorrect specifications will mislead the code agent; there is no guarantee the first-stage output is correct.
3. **Scalability to Large Programs**: Evaluated on ProgramBench (200 instances); unclear how well this scales to larger, more complex real-world applications with many functions, modules, or intricate state machines.
4. **Cost and Latency**: Two-stage processing requires two full inference passes; doubles computational cost and latency compared to single-pass baselines — may be prohibitive in latency-sensitive or resource-constrained settings.
5. **Documentation Quality**: The approach assumes documentation is available and reasonably accurate. If documentation is absent or misleading, the spec agent's exploration becomes the bottleneck, and gains may diminish.
6. **Model Capability Floor**: Improvements are shown for frontier and near-frontier models; unclear whether the same benefits hold for smaller or weaker models that may struggle to write formal specifications.

## Open Questions
1. **Specification Correctness**: Can we validate or verify the specification itself before passing it to the code agent? Should there be a third validation stage or feedback loop?
2. **Cross-Model Generalization**: Can a specification written by a weaker spec agent be effectively used by a stronger code agent, or does model consistency matter?
3. **Human-in-the-Loop**: Where and how should humans intervene in the pipeline to correct or refine specifications? What is the UX and cost-benefit?
4. **Specification Format**: Is the current specification format optimal, or could structured (e.g., formal logic, state machines) or semi-structured (e.g., assertions, invariants) formats improve code synthesis further?
5. **Partial Specifications**: Can SpecFirst work well with incomplete or probabilistic specifications (e.g., "this function probably does X, but might do Y")? How does uncertainty in the spec stage propagate?
6. **Real-World Evaluation**: How does SpecFirst perform on real open-source or industrial codebases, where binaries may be stripped, documentation sparse, and behavior non-deterministic?

## Key Takeaway
Separating behavioral specification elicitation from code synthesis improves LLM agent performance on from-scratch program generation by 7–21%.
