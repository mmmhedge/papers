# Verify Claims, Not Scores: Evidence-Based Verification of Modular Agents

**Authors:** Ali Atiah Alzahrani
**Published:** 2026-10-01 | **arXiv:** [2610.01348v1](http://arxiv.org/abs/2610.01348v1)

## Summary
This paper proposes a new way to evaluate modular AI agents by auditing the *evidence* behind their decisions rather than just looking at overall performance scores. The approach tracks what each component (planner, actor, verifier) contributes to outcomes and whether those contributions are actually justified, using a portfolio-allocation agent as a test case. This matters because swapping one component for another in an agent gives you no insight into which part broke, what the agent is actually checking, or whether improvements are real or just artifacts of how you measured them.

## Theoretical Background
The paper builds on agent architectures that decompose decision-making into modular stages: planning (deciding what to do), acting (executing), checking (verifying outcomes), and refining (learning). It connects to work on [[reinforcement-learning]] verification and interpretability — the idea that we should understand *why* an agent makes a decision, not just measure whether it works. The foundational tension is that aggregate task scores (standard in RL and quantitative finance) hide component-level failures and can make spurious improvements look real. The paper also draws on oracle policy analysis from computational RL: a perfect policy under a given action set tells you the ceiling of what's possible, so if actual performance lags far behind, you know the agent itself is broken, not the environment.

## Core Contributions
1. **Claim-specific verification audit protocol**: A structured methodology to score *evidence* rather than outcomes, assigning verdicts (supported, unsupported, unresolved, not evaluated) to each claim an agent makes, with explicit boundary conditions.
2. **Oracle policies for interpretability**: Using a perfect policy within the agent's stated action set to separate agent-failure from environment-difficulty, and making null results meaningful by tracking whether downstream components could mask the signal.
3. **Verifier validity testing**: A separate diagnostic test that checks whether the agent's own runtime verification actually bounds what it claims to bound — and in the portfolio case, showing it can be bypassed entirely without visible degradation.
4. **Empirical application to portfolio allocation**: Demonstration that regime information value depends on the action set; that scenario generation can discard most signal; and that local fidelity gains don't always translate to decision improvements.

## Connections to Other Work
This work sits at the intersection of [[mechanistic-interpretability]] (understanding what components contribute), agent reliability (e.g., work on trustworthy RL), and financial risk-management audit methodologies. It critiques the standard [[reinforcement-learning]] evaluation paradigm where a single reward signal obscures component faults — a theme also present in work on interpretability of learned models and [[alignment]]-adjacent concerns about verifying agent behavior. The portfolio-allocation domain connects to quantitative finance but the core contribution is methodological: a verification protocol applicable to any modular agent system.

## Practical Applications
1. **Quantitative finance**: Portfolio managers and risk teams can audit trading agents before deployment by checking whether regime detectors actually work, whether risk verifiers are enforcing constraints, and whether improving a sub-component (e.g., forecast model) actually moves the needle on final decisions.
2. **Autonomous systems development**: Before releasing a multi-stage autonomous system (e.g., perception → planning → safety-check → action), teams can trace exactly which component failed and whether the safety verifier is real or decorative.
3. **Regulatory compliance audits**: Financial firms and other regulated industries can document not just that an agent performed well, but *why* it performed well and which checks actually mattered — critical for explaining decisions to regulators or after failures.
4. **Model debugging in production**: When a deployed agent's performance drops, this audit protocol isolates whether the issue is the controller, the learned model, or the verifier — avoiding blind rewrites.

## Product & Startup Ideas
1. **Agent audit-as-a-service platform**: A SaaS tool that automatically ingests a modular agent's logs (plans, actions, checks, outcomes) and runs the audit protocol, producing a report that shows which components are adding value and which are decorative — targeting fintech and autonomous-systems firms.
2. **Verifier validation software**: Specialized tool for quantitative finance firms to test whether their risk and compliance verifiers actually enforce what they claim, with automated false-bypass detection — reduces audit costs and regulatory risk.
3. **Component replacement testing toolkit**: Library + CI/CD integration for RL teams to safely swap agents' sub-components (e.g., swapping a controller) and automatically run the audit to show exactly what was gained or lost, with oracle baselines baked in.
4. **Interpretable portfolio agent builder**: A framework that helps portfolio managers build modular trading agents with built-in claim auditing, letting them understand (and defend in court) exactly why each decision was made.
5. **Regulatory compliance AI auditor**: Consulting service + software that works with financial institutions to audit their deployed agents against this protocol, producing defensible documentation for regulators and internal governance boards.

## Technical Limitations
1. **Oracle policy requires known action set**: You need to be able to define and exhaustively solve (or bound) a perfect policy under the agent's stated action set. In high-dimensional or continuous action spaces, this becomes intractable.
2. **Masking and downstream coupling**: The protocol acknowledges that null results are "unresolved" if downstream components could mask failures, but doesn't provide a systematic way to *control* for this — you have to guess which interactions matter.
3. **Synthetic environment**: The empirical validation is in a synthetic market with known hidden regimes. Real markets have regimes the audit itself won't detect, and the verifier's role may be more subtle when the environment is non-stationary in unexpected ways.
4. **Verdicts require ground truth**: Assigning "supported" vs. "unsupported" requires knowing what the truth is (e.g., the true regime). This is feasible in simulation but hard in real deployments where regimes are latent.
5. **Computational overhead**: Running oracle policies, component swaps, and verifier tests on top of agent execution is expensive. Scaling to high-frequency or large-scale systems is unclear.
6. **Generalization across domains**: The paper tests on portfolio allocation. Whether the audit protocol is equally informative for other agent architectures (e.g., language-agent loops, multi-agent teams) is not addressed.

## Open Questions
1. **How do you handle multi-agent or hierarchical agents?** The protocol assumes a linear pipeline (plan → act → check → refine). What breaks if you have nested agents or peer agents that coordinate?
2. **Can you automate the oracle policy construction?** Right now you manually design the action set and solve for the perfect policy. For complex domains, is there a way to learn or approximate oracles without expert knowledge?
3. **How do you extend this to continuous, partially observable environments?** The portfolio case is discrete regimes in a known state space. How does the audit scale to POMDPs or high-dimensional continuous control?
4. **What role does timing play?** If components operate on different timescales (e.g., a slow verifier and a fast controller), does the audit still isolate failures cleanly?
5. **Can you use this to guide agent *design*, not just debug?** Right now it's a post-hoc audit tool. Could it drive automatic component search or removal?
6. **How do verdicts change over non-stationary environments?** In real markets, regimes shift. Can the audit be run online to detect when the verifier or planner has become stale?

## Key Takeaway
Audit modular agents by testing whether each claim is actually supported by evidence, not by looking at overall scores alone.
