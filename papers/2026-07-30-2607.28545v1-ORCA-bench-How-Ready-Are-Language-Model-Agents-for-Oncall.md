# ORCA-bench: How Ready Are Language Model Agents for Oncall?

**Authors:** Albert Gong, Kyuseong Choi, Abhineet Agarwal, Jason Schechner, Ryan Huang et al.
**Published:** 2026-07-30 | **arXiv:** [2607.28545v1](http://arxiv.org/abs/2607.28545v1)

## Summary
This paper introduces ORCA-bench, a benchmark that evaluates how well AI coding agents can perform oncall root cause analysis (RCA)—the task of diagnosing why production systems fail. The authors test five frontier language models against 1,079 realistic incidents in a production-fidelity testbed with real metrics, logs, and code, and find that even the best models only achieve 25.3% accuracy on medium-difficulty cases and 10.0% on hard cases, revealing a significant gap before these agents can safely handle real production systems.

## Theoretical Background
This work builds on recent advances in [[Large Language Models]] (LLMs) for code understanding and reasoning—models like Claude and GPT-4 can write, debug, and search code through natural language. However, oncall RCA is a different problem: it requires multi-modal reasoning across noisy, time-sensitive signals (metrics from Prometheus, distributed traces from Jaeger, logs from OpenSearch) combined with source-code analysis, starting from ambiguous user reports. The benchmark leverages OpenTelemetry—an industry standard for instrumenting microservices—to create a realistic evaluation setting. The authors use an LLM-as-judge approach for scoring, validated against human raters (Cohen's κ_w = 0.90, indicating strong inter-rater agreement).

## Core Contributions
1. **ORCA-bench itself**: A production-fidelity benchmark with 1,079 RCA tasks spanning systematic variations in report specificity, time-to-detection, and concurrent faults—not toy examples, but real incident scenarios curated and validated by expert SREs.
2. **Quantified capability gaps**: Empirical demonstration that frontier models achieve only 10–25% accuracy, with models hallucinating plausible-sounding but false root causes in ~40% of cases.
3. **Impact analysis**: Controlled ablations showing source-code access is critical (all metrics degrade without it), and measuring sensitivity to task difficulty.
4. **Honest lower-bound framing**: The authors argue their curated 50 GB testbed represents a lower bound on the gap—real production systems are orders of magnitude larger, more dynamic, and less transparent, so the true engineering investment needed is even larger.

## Connections to Other Work
This relates to broader efforts in evaluating [[agents]] on real-world tasks beyond toy benchmarks. It echoes concerns in [[alignment]]—particularly around AI systems making high-stakes decisions with incomplete information. The multi-modal reasoning challenge (combining structured metrics, unstructured logs, code, and natural language) connects to work on grounding language models in external tools and APIs. The finding that access to source code matters aligns with observations that code understanding benefits from full context, and the hallucination problem is a known [[large-language-models]] failure mode in high-stakes settings.

## Practical Applications
1. **Automated incident response**: Using LLM agents as first responders to triage and diagnose production incidents, with human SREs validating or overriding suggestions.
2. **On-call assistant tools**: IDE or observability platform plugins that suggest likely root causes, candidate fixes, or runbook steps as SREs investigate.
3. **Training and onboarding**: Using benchmark tasks to train junior SREs on real incident patterns, or to evaluate SRE hiring and readiness.
4. **Observability system design**: Using RCA failure modes to inform which metrics, logs, and traces teams should instrument (e.g., which signals would most improve agent performance).

## Product & Startup Ideas
1. **LLM-powered SRE co-pilot**: A SaaS observability add-on that continuously monitors for anomalies, suggests root causes in natural language, links to runbooks, and learns from SRE feedback—positioning itself as the "Copilot for on-call."
2. **Incident RCA-as-a-service**: A managed service that ingests your observability data and returns structured RCA reports, reducing toil for under-staffed teams and creating an audit trail for post-mortems.
3. **Benchmark-as-a-service for SREs**: A platform that lets organizations run incident diagnosis benchmarks on their own production data (anonymized) to identify observability gaps or LLM capability shortfalls specific to their stack.
4. **Observability data pre-processor**: A tool that auto-selects, correlates, and ranks the most relevant metrics/logs/traces to feed to LLM agents, improving signal-to-noise and agent accuracy.
5. **SRE hiring and skills platform**: Use ORCA-bench-style tasks as a standardized assessment for SRE competence, certifications, or platform-specific expertise.

## Technical Limitations
1. **Curated environment is cleaner than reality**: The 50 GB, six-day testbed is public and well-instrumented; real production systems are messy, larger, and instrumentation gaps are common.
2. **Isolated incident evaluation**: Tasks are investigated in isolation, but real oncall often involves context from previous incidents, seasonal patterns, or cascading failures across teams' systems.
3. **No agent learning or feedback loops**: The benchmark is a one-shot evaluation; it does not test whether agents improve with human feedback or if they can generalize to entirely new systems.
4. **Limited to diagnosis, not remediation**: RCA is one step; actually running fixes, rollbacks, or escalations is a separate (and potentially higher-stakes) problem not addressed here.
5. **Hallucination remains unsolved**: Even with access to real data, models confidently propose false root causes; no guardrails or uncertainty quantification are demonstrated.
6. **No cost-performance trade-off analysis**: The paper does not explore whether cheaper, smaller models or few-shot prompting could close the gap, only that frontier models fall short.

## Open Questions
1. **Can agents improve with feedback?** Does retraining or fine-tuning on ORCA-bench examples, or using RLHF on SRE feedback, close the accuracy gap? How much curated feedback is needed?
2. **Generalization across systems**: Do agents trained on one microservice architecture transfer to others, or does each new system require retraining?
3. **Why does source code help?** Is it code search, understanding dependency graphs, or semantic understanding of business logic? Deeper analysis of code's role could guide future tool design.
4. **Can weaker models + better prompting compete?** With chain-of-thought, retrieval-augmented generation (RAG), or multi-step reasoning, can smaller models match frontier model performance?
5. **What about cascading and systemic failures?** How do agents perform when root cause is "it's actually two unrelated bugs that happen to trigger together"?
6. **Human-in-the-loop designs**: What interaction patterns (e.g., agents propose top-3 hypotheses, SRE narrows down) would best combine agent speed with human reliability?

## Key Takeaway
State-of-the-art language models achieve only 10–25% accuracy on production incident diagnosis, revealing they are not yet ready for autonomous oncall work.
